## 1. Executive Summary & Component Boundaries

SF-04 delivers the complete architecture for measuring Salesforce Developer Edition org capacity, bounding Salesforce data projections to compact candidate tracking entities, versioning and staging project-owned metadata without leaking org assets or credentials, and generating cryptographically verified candidate-owned data exports for inclusion in OPS-01 disaster recovery backups.

### 1.1 Strict Non-Mutation & Data Preservation Boundaries
In strict compliance with repository instructions, blueprint §§5–6, and `docs/stories/SF-04.md`:
- **No Record Deletions at Capacity**: SF-04 **never** silently deletes or prunes Salesforce or local records when storage is full. Exhausted capacity triggers a visible `CAPACITY` error and defers new publications while preserving queued sync steps and local normalized postings.
- **Metadata Portability Separate from Data Backup**: XML metadata source and manifests recreate configuration; they do **not** backup candidate notes, application history, or credentials. Candidate exports preserve observed business data, not deployable schemas.
- **Read-Only Remote Operations**: Metadata retrieval and data export execute strictly read-only remote queries (`get_limits`, `query_page`). No records, metadata, or permission policies are mutated on the remote org.
- **Strict Credential & Org Isolation**: Credentials, tokens, private keys, client secrets, and unrelated org objects (e.g. standard Account/Contact, Admin profiles) are strictly excluded from tracked files, manifests, and exports.
- **Inert Restoration**: Recovery packages and restored datasets remain completely inert (zero outbound network or sync traffic).

## 3. Metadata Allowlist and Ownership Inventory

### 3.1 Scoped Retrieval Allowlist (`salesforce/manifest/sf04-retrieve.xml`)
Packages the complete project-owned metadata footprint:
- **`CustomApplication`**: `Job_Tracker`
- **`ExternalClientApplication`**: `Job_Automation_Client` (OAuth 2.0 PKCE)
- **`ExtlClntAppOauthSettings`**: `Job_Automation_Client`
- **`ExtlClntAppOauthConfigurablePolicies`**: `Job_Automation_Client`
- **`CustomObject`**: `Company__c`, `Job__c`
- **`CustomField`**: 4 Company fields + 17 Job fields (21 total)
- **`ValidationRule`**: 4 UUID immutability and format rules (2 Company, 2 Job)
- **`CompactLayout`**: `Job__c.JA_Tracking`
- **`ListView`**: 7 candidate tracking list views
- **`Layout`**: `Job__c-JA Candidate Tracking`, `Company__c-JA Company Overview`
- **`FlexiPage`**: `JA_Job_Tracking`
- **`CustomTab`**: `Company__c`, `Job__c`
- **`ReportType`**: `JA_Jobs`
- **`ReportFolder`**: `Job_Tracker`
- **`Report`**: 4 candidate tracking reports
- **`PermissionSet`**: `Job_Automation_Worker`

### 3.2 Member Ownership Registry (`salesforce/metadata-ownership.json`)
Categorizes metadata members into:
- `project-owned`: Scoped assets above.
- `shared-dependency`: Read-only platform entities (`User`).
- `unrelated-protected`: Standard CRM objects (`Account`, `Contact`, `Lead`, `Opportunity`), broad administrative profiles (`System Administrator`, `Admin`, `Standard User`), and non-project Connected Apps.
- `unknown`: Any unlisted file.

The staging auditor quarantines any unowned file and halts promotion if secrets or broad profiles are detected.

## 5. Candidate Data Export & Independent Verification

### 5.1 Export Package Structure
Export packages are written atomically to `local_data/exports/export_<uuid>_<scan_id>/`:
1. `manifest.json`: Top-level signed manifest with scan ID, UTC timestamps, record counts, file hashes, and completeness status.
2. `companies.jsonl`: Parent `Company__c` rows with canonical company UUIDs.
3. `jobs.jsonl`: Tracked `Job__c` rows with canonical job UUIDs, resolved company lookups, and all 5 candidate fields.
4. `snapshots.jsonl`: Historical candidate snapshots retrieved from SQLite storage.
5. `history.jsonl`: Observed `Job__History` change records.
6. `issues.jsonl`: Actionable issue register (missing parents, invalid IDs).

### 5.2 Verification Safeguards (`verify_export_package`)
- Independent SHA-256 byte-for-byte checksum verification.
- Path traversal and directory escape rejection.
- Unique canonical UUID validation.
- Parent Company relationship closure verification.

## 6. OPS-01 Disaster Recovery Integration

### 6.1 Unified Backup Manifest Integration
When an export package is available, `create_backup` automatically copies export files into `remote_export/` in the backup archive and registers each file's SHA-256 hash in `manifest.files`.
