## 1. Executive Summary & Component Scope

SF-06 delivers the Lightning UI action surface, screen flows, option catalogs, and an atomic invocable submission service for enqueuing CV and Cover Letter document generation requests directly from the `Job__c` tracking interface. It provides an idempotent, concurrency-safe boundary that handles active duplicate request reuse, deliberate draft regeneration, and explicit unavailable-job consent gating, completely decoupling the Salesforce tracking interface from the local Windows model runtime.

### 1.1 Core Architectural Guarantees

1. **Decoupled Asynchronous Queueing (Zero Localhost / Local Worker Calls)**:
   Neither Flow, Apex, nor QuickAction attempts synchronous HTTP callouts or connects to localhost. When a candidate submits an action, a new record is created with initial status `Pending` (or an identical active request is reused). The request remains safely queued in Salesforce awaiting asynchronous pull-based discovery by the local Windows worker process (GEN-01).
2. **Accurate User Feedback When Worker is Offline**:
   Feedback screens explicitly notify the candidate that the request has been safely queued in Salesforce and will be processed automatically when the local worker process is running on their Windows computer.
3. **Atomic Active Duplicate Reuse**:
   If an active request (`Pending`, `Running`, `Upload_Pending`) exists for the current candidate with identical options (`Job__c`, `Document_Type__c`, `Language__c`, `Template_Id__c`, `Context_Strategy__c`, and `Allow_Unavailable_Job__c`), the service reuses the existing request. It does **not** create duplicate records, reset timestamps, or alter worker operational fields.
4. **Idempotency Replay via Submission Receipts (`JA_Generation_Submission__c`)**:
   Every submission intent is bound to a deterministic receipt keyed by `UserId:SubmissionToken`. Resubmission of the same token with identical parameters returns `replayed` with the original request and its current state. Resubmission with conflicting parameters is rejected without modifying database records.
5. **Deliberate Regeneration with Lineage Preservation**:
   Deliberate regeneration creates a brand new `Generation_Request__c` with a unique AutoNumber identity (`GR-{000000}`) and sets `Predecessor_Request__c` to link lineage. Prior drafts and delivered artifacts are fully preserved.
6. **Unavailable Job Consent & Failure History Invariants**:
   `Allow_Unavailable_Job__c` defaults strictly to `false`. Target jobs marked `Unavailable` require explicit candidate checkbox consent. If a prior request failed with `job_unavailable`, ordinary creation is gated: the candidate must deliberately regenerate with an explicit true override.
7. **Parent Job Locking & Concurrency Safety**:
   Transactions lock the target `Job__c` row via `SELECT ... FOR UPDATE` before evaluating active requests or inserting receipts. Row lock contention returns a safe `retryable_conflict` response.
8. **Candidate Tracking Field Immutability**:
   Submission actions insert or reuse generation requests only; candidate tracking fields (`Application_Progress__c`, `Candidate_Notes__c`, `Candidate_Decision__c`, `Follow_Up_Date__c`) on `Job__c` remain strictly untouched.

## 5. Downstream Integration Requirements

### 5.1 GEN-01: Ingestion & Polling Discovery
- The worker polls for `Pending` records using `RequestFieldMapping.build_soql_query()`.
- Newly created requests have `Client_Request_Key__c = null`. GEN-01 deterministically computes local UUIDv5 via `derive_local_request_id(org_id, canonical_sf_id)`.
- Reused active requests or deliberate regeneration successors preserve stable local identities without duplication.

### 5.2 GEN-02: Input Freezing & Availability Recheck
- At claim time, GEN-02 evaluates actual availability. If a previously active job is now closed and `Allow_Unavailable_Job__c == false`, GEN-02 fails the request with `Error_Reason__c = "job_unavailable"`.
- This failure is inspectable by SF-06 to enforce explicit override consent on subsequent regeneration attempts.

### 5.3 SF-07: Document Approval & File Linking
- Once the worker delivers artifacts and sets `Status__c = "Ready_for_Review"`, SF-07 provides candidate approval controls (`draft`, `approved`, `superseded`).
- Completion of generation never automatically approves the document or advances candidate application progress on `Job__c`.
