## 1. Executive Summary & Component Scope

SF-02 delivers the complete integration authorization architecture, scoped Salesforce metadata, native Windows DPAPI credential provisioning helpers, and offline verification suite required to securely connect the personal job search automation worker to the user's existing Salesforce Developer Edition Org (`dev-main`).

### 1.1 Strict Security & Non-Mutation Boundaries
In compliance with repository instructions, blueprint §5, and `docs/stories/SF-02.md`:
- **Selected Authorization Flow**: External Client App (ECA) using OAuth 2.0 Web Server (Authorization Code) Flow with **PKCE S256**, followed by non-interactive refresh-token renewals.
- **Zero Software Licensing Cost**: Relies exclusively on the user's existing Developer Edition entitlements; does not require purchasing a paid Salesforce Integration user seat.
- **No Client Secret or Private Key on Disk**: Configured for public installed client semantics with PKCE (`isConsumerSecretOptional = true`, `isSecretRequiredForRefreshToken = false`). No client secret, certificate, or private key is generated, stored, logged, or committed to source control.
- **Strictly Scoped Permissions**: Authored `Job_Automation_Worker` permission set with least-privilege CRUD on `Company__c` and `Job__c` (Read, Create, Edit; **No Delete**, **No View/Modify All**), FLS Read-Write on machine fields, and **Strictly Read-Only** on candidate-owned tracking fields (`Application_Progress__c`, `Candidate_Notes__c`, etc.) to enforce candidate preservation.
- **Native Windows DPAPI Storage**: Credentials (`salesforce/client_id` and `salesforce/refresh_token`) are encrypted via Windows DPAPI (`CryptProtectData`) and stored in `%LOCALAPPDATA%\JobAutomation\credentials\`, completely outside the repository.
- **No Gate Widening or SFCLIENT-01 Gateway Modification**: Reused existing SFCLIENT-01 contracts (`SalesforceSettings`, `OAuthTokenProvider`, `WindowsDpapiCredentialStore`, `UrllibHttpTransport`) without modifying gateway logic or expanding access to mask configuration errors.
- **Live Remote Org Status**: In strict adherence to authorization rules, **no unauthenticated remote calls, forged credentials, or live record mutations were executed**. All 19 applicable matrix scenarios pass offline; unavailable live checks are explicitly cataloged.

## 3. Current Salesforce Platform Requirements Verification

Official Salesforce platform documentation and release notes (*External Client Apps Guide*, *Remote Access OAuth*, *Spring '26 Release Notes*) were verified on **01 November 2026**:

1. **Connected App Deprecation**:
   - Starting in Spring '26, creation of new Connected Apps is restricted across all orgs in favor of External Client Apps (ECAs). Existing connected apps continue to function, but newly introduced integrations must use ECAs to remain supported.
2. **Web Server Flow with PKCE (Proof Key for Code Exchange)**:
   - Salesforce mandates PKCE for mobile and desktop user-agent flows. RFC 7636 PKCE S256 is supported natively by ECAs (`<isPkceRequired>true</isPkceRequired>`).
3. **Public Client (Secret-Free) Installed Client Support**:
   - ECAs explicitly support secret-free web server authorization and refresh token exchanges for native installed applications via `<isConsumerSecretOptional>true</isConsumerSecretOptional>` and `<isSecretRequiredForRefreshToken>false</isSecretRequiredForRefreshToken>`.
4. **Loopback Redirect URI Restrictions**:
   - Salesforce natively supports loopback redirects (`http://localhost:<port>/<path>`) for installed CLI and desktop apps. Port `1717` with path `/OauthRedirect` is the platform standard.
5. **Scopes & Token Lifecycles**:
   - Scopes `Api` (`api`) and `RefreshToken` (`refresh_token` / `offline_access`) provide the minimum necessary privileges for REST CRUD operations and background session renewal.
   - Configurable policies support finite token lifetimes (e.g. 90 days) and session timeouts (15 minutes).

## 6. Native Windows Credential Setup and Operating Instructions

### 6.1 Private Storage Architecture
1. **Directory Location**: `%LOCALAPPDATA%\JobAutomation\credentials\` (constructed via `Join-Path $env:LOCALAPPDATA 'JobAutomation\credentials'`).
2. **DPAPI Encryption**: Every credential value is encrypted via Windows Data Protection API (`CryptProtectData`) bound to the current Windows user's logon session (`pbData` passed to `crypt32.dll`).
3. **Safe Storage Mapping**: References map to hashed binary files:
   - `salesforce/client_id` -> `%LOCALAPPDATA%\JobAutomation\credentials\salesforce_client_id_<hash>.bin`
   - `salesforce/refresh_token` -> `%LOCALAPPDATA%\JobAutomation\credentials\salesforce_refresh_token_<hash>.bin`
4. **NTFS Access Control List (ACL)**:
   - Only the executing Windows user account and `SYSTEM` have access. Broad groups (`Users`, `Everyone`, `Authenticated Users`) must be removed from the credential folder:
   ```powershell
   $credDir = Join-Path $env:LOCALAPPDATA 'JobAutomation\credentials'
   icacls $credDir /inheritance:r /grant:r "$($env:USERNAME):(OI)(CI)F" "SYSTEM:(OI)(CI)F"
   ```

## 7. Operational Runbooks

### 7.1 One-Time Interactive PKCE Enrollment
When the operator has registered the External Client App in Salesforce Setup and obtained the Consumer Key (Client ID):

```powershell
# Execute the interactive enrollment helper
& '.\scripts\windows\authorize_salesforce.ps1' -Config 'config\salesforce.json' -ClientId '<ECA_CONSUMER_KEY>'
```

**Procedure Flow**:
1. The script verifies that port `1717` is available and starts a transient loopback listener on `127.0.0.1:1717`.
2. Generates a fresh RFC 7636 PKCE `code_verifier` and S256 `code_challenge`, plus a high-entropy CSRF `state` token.
3. Automatically launches the system default browser navigating to the Salesforce authorization page.
4. The user authenticates and clicks **Allow**.
5. Salesforce redirects to `http://localhost:1717/OauthRedirect?code=...&state=...`.
6. The loopback receiver validates the state, closes the listener, exchanges the code with PKCE for a refresh token via HTTPS POST, verifies that the returned Org ID matches `expected_org_id`, encrypts the credentials into Windows DPAPI, and renders a success confirmation in the browser.
