## 3. Schema Inventory & Collision Register

The pipeline tracking architecture requires synchronizing evaluated vacancies into two custom objects: `Company__c` and `Job__c`.

### 3.1 Required Mapping Checklist (Conforming to `SYNC-01` Schema 1.0)
- **`Company__c`**:
  - `Canonical_Company_Id__c`: Text(255), External ID, Unique (Case-Insensitive), Required.
  - `Name`: Text(255), Standard Name field for Employer Name.
  - `Sync_Operation_Marker__c`: Text(255), Indexed Text. Reconciliation marker.
  - `Machine_Sync_Version__c`: Number(18, 0), Monotonic entity sequence.
- **`Job__c`**:
  - `Canonical_Job_Id__c`: Text(255), External ID, Unique (Case-Insensitive), Required.
  - `Name`: Text(255), Standard Name field for Job Title (or `Title__c` if Name is Autonumber).
  - `Company__c`: Lookup relationship to `Company__c` (`deleteConstraint="SetNull"`).
  - `Availability__c`: Picklist (`Active`, `Not Seen`, `Unavailable`, `Unknown`).
  - `Assessment_Disposition__c`: Picklist (`Eligible`, `Review`, `Rejected`).
  - `Assessment_Reasons__c`: Long Text Area (32,768).
  - `Relevance_Score__c`: Number(5, 2), Nullable (null for rules-only).
  - `Score_Scale__c`: Text(50), Nullable (null for rules-only).
  - `Last_Evaluated_At__c`: DateTime (UTC ISO-8601).
  - `Source_URLs__c`: Long Text Area (32,768).
  - `Sync_Operation_Marker__c`: Text(255), Reconciliation marker.
  - `Machine_Sync_Version__c`: Number(18, 0), Monotonic entity sequence.
- **Candidate-Owned Fields on `Job__c` (Strictly Protected Against Overwrite)**:
  - `Application_Progress__c`: Picklist (`New`, `Review`, `Shortlisted`, `Applied`, `Interviewing`, `Offer`, `Rejected`, `Withdrawn`, `Archived`). Defaults to `New` on creation via Salesforce metadata; never reapplied by sync.
  - `Candidate_Notes__c`: Long Text Area.
  - `Candidate_Decision__c`: Picklist / Text.
  - `Follow_Up_Date__c`: Date.
  - `Interview_Date__c`: DateTime.

### 3.2 Collision & Usability Risk Register

| Asset | Potential Org Collision | Risk & Failure Mode | Pre-Planned Resolution |
|---|---|---|---|
| **`Job__c.Name`** | Standard Name is Autonumber (`JOB-{0000}`). | Passing title in `{"Name": "..."}` fails on upsert. | Map custom field `Title__c` (Text 255) and configure `config/sync.json` (`title_field: "Title__c"`). |
| **`Job__c` / `Company__c`** | Unrelated custom objects exist from Trailhead / older apps. | Field type mismatches, validation errors, or data corruption. | Adopt project prefix: `JS_Job__c` and `JS_Company__c`. Update `config/sync.json` mappings without touching existing objects. |
| **External IDs** | `Canonical_*_Id__c` exists but lacks `unique` flag. | REST upsert will fail if duplicate values exist in the org. | Verify uniqueness via Describe. Clean legacy duplicates if necessary before enforcing constraint. |
| **Picklists** | Restricted picklist values differ in spelling/case. | Upsert fails with `INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST`. | Ensure org picklist values match `SYNC-01` mappings exactly (`Eligible`, `Review`, `Rejected`, etc.). |

## 5. Org Capacity & Zero-Budget Storage Architecture

Official Salesforce documentation confirms standard Developer Edition allocations:
- **Data Storage**: 5.0 MB (~2,560 records at 2 KB per record convention).
- **File Storage**: 20.0 MB.
- **Daily API Requests**: 15,000 calls per rolling 24-hour window.

### 5.1 Critical Architectural Rules for Personal Automation ([R14](../../IMPLEMENTATION_BLUEPRINT.md#r14), [R16](../../IMPLEMENTATION_BLUEPRINT.md#r16))
1. **Raw Data Stays Local**: Raw posting HTML, unstructured descriptions, candidate profile evidence, RAG embeddings, and verbose execution logs **must remain in local SQLite** (`%LOCALAPPDATA%\JobAutomation\storage\job_search.db`).
2. **Selective Tracking**: Only `Eligible` and `Review` jobs enter Salesforce. Confirmed `Rejected` jobs remain strictly local.
3. **Data Storage Footprint**:
   - Tracking 200 jobs + 100 companies = 300 records = **600 KB** (~11.7% of org capacity).
   - Tracking 500 jobs + 250 companies = 750 records = **1.5 MB** (~29.3% of org capacity).
4. **File Storage Footprint (Phase 1 GEN-06)**:
   - Generated CV/letter PDFs (~250 KB pair) allow storing **45–80 document versions** in Salesforce before hitting 20 MB. Local disk remains the primary artifact archive; older remote drafts must be archived.
5. **API Quota Consumption**:
   - A typical sync batch consumes **< 150 API calls/day (< 1.0% of the 15,000 daily limit)**. API quota is not a bottleneck.

## 6. Authentication Architecture & No-New-Cost Recommendation

### 6.1 Evaluation of Options for Developer Edition
1. **OAuth 2.0 Web Server / Authorization Code Flow with Refresh Token (and PKCE)**:
   - **Recommendation**: **PRIMARY RECOMMENDED FLOW (SF-02)**.
   - **Justification**: 100% free; runs under user's existing System Administrator user without requiring an additional paid user seat.
   - **Code Readiness**: `OAuthTokenProvider` in `src/job_automation/salesforce/auth.py` is already implemented and verified with Windows DPAPI.
2. **JWT Bearer Flow**: Feasible in Dev Org, but represents a code gap in `SFCLIENT-01` (client only implements refresh token exchange).
3. **Client Credentials Flow**: Problematic in Developer Edition due to execution user licensing restrictions; not implemented in client.
4. **CLI Token Hijacking**: Strictly prohibited under R15 security rules.

### 6.2 External Client App (ECA) Guidance
Salesforce enforces the transition from Connected Apps to **External Client Apps (ECAs)** starting Spring '26. SF-02 should register an External Client App (`Job_Automation_Client`) with scopes `api` and `refresh_token, offline_access`.

## 8. Read-Only Live Inspection Procedure

When the user confirms the intended target org and provisions credentials, the following read-only inspection procedure must be executed:

### Option A: Via Python Gateway (Recommended / Zero External Tooling)
1. Configure `config/salesforce.json` with the confirmed `instance_url` and `expected_org_id`.
2. Run the SF-02 bootstrap script to store the refresh token into Windows DPAPI.
3. Execute the safe read-only smoke check:
   ```powershell
   & ".\.venv\Scripts\python.exe" ".\tests\manual\salesforce_smoke.py" --config "config\salesforce.json"
   ```
4. Verify output:
   - Gate 1: Connection Check (returns Org ID and confirmed API version).
   - Gate 2: API Limits Check (returns `daily_api_requests_remaining`).
   - Gate 3: Describe Object (returns status of `Job__c` and `Company__c`).

### Option B: Via Salesforce CLI (`sf` / `sfdx`)
If the user prefers using Salesforce CLI:
```powershell
# 1. Authorize the confirmed target org
sf org login web --alias job-search-dev --instance-url https://<my-domain>.develop.my.salesforce.com

# 2. Inspect org identity and edition
sf org display --target-org job-search-dev

# 3. Read API limits
sf limits api display --target-org job-search-dev

# 4. Describe candidate objects
sf sobject describe --sobject Job__c --target-org job-search-dev
sf sobject describe --sobject Company__c --target-org job-search-dev
```

### Option C: Via Salesforce Setup UI
1. Log into Salesforce in a web browser.
2. Check **Company Information** (`Setup -> Company Settings -> Company Information`): Confirm Org Edition (Developer Edition) and Org ID.
3. Check **Storage Usage** (`Setup -> Company Settings -> Storage Usage`): Confirm Data Storage MB and File Storage MB remaining.
4. Check **Object Manager** (`Setup -> Objects and Fields -> Object Manager`): Search for `Job` and `Company` to confirm existence or collision.
