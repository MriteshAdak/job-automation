## 1. Executive Summary & Component Scope

`GEN-06` delivers validated, rendered artifact sets (`.docx` and `.pdf`) from local managed storage to remote Salesforce Files (`ContentVersion`, `ContentDocument`, `ContentDocumentLink`). It enforces the strict boundary between delivery readiness and candidate approval: delivered files remain strictly in `draft` approval status, readiness projection never precedes verified candidate accessibility, and failure to upload or link never discards physical files or loses work.

### Core Architecture & Behavioral Invariants

1. **Intent-Before-Send Checkpoints (Migration 015)**:
   - Every physical upload is preceded by a durable `DeliveryIntent` record committed to SQLite.
   - The intent records the exact byte hash (`sha256:...`), file size, target Salesforce request ID, canonical Salesforce job ID (if available), format, and immutable reconciliation marker.
2. **Reconciliation Markers & Lost-Response Recovery**:
   - Every uploaded artifact embeds a unique, deterministic reconciliation marker:
     `gen06:v1:<request_uuid>:<artifact_uuid>:<artifact_version>`
   - If network or server disconnection interrupts an upload response, the recovery logic queries Salesforce by marker before retrying. An `EXACT_MATCH` adopts the existing `ContentVersion` without duplicate upload; a `PROVEN_ABSENT` allows fresh upload; an ambiguous or multi-record `CONFLICT` halts for intervention.
3. **Multi-Format Atomic Commitment & Candidate Accessibility Gating**:
   - `ContentDocumentLink` records link the uploaded files to the target Salesforce `Generation_Request__c` (and optionally `Job_Posting__c`).
   - Prior to sealing the `DeliverySetReceipt` and advancing the request to `ready_for_review`, the accessibility gate (`verify_candidate_access`) verifies that:
     * A valid link exists to the target record with `ShareType IN ('V', 'C', 'I')`.
     * `Visibility` is set to `'AllUsers'`.
     * If linking or sharing verification fails, the delivery set is NOT accessible, and transition to `ready_for_review` is blocked.
4. **Preservation of `upload_pending` and Local Files**:
   - If Salesforce storage quotas are exceeded (`STORAGE_LIMIT_EXCEEDED` -> `ErrorCategory.CAPACITY`), permissions are lacking (`INSUFFICIENT_ACCESS` -> `ErrorCategory.PERMISSION`), or network limits occur (`REQUEST_LIMIT_EXCEEDED` -> `ErrorCategory.RATE_LIMIT`), the request remains strictly in `upload_pending`.
   - Physical `.docx` and `.pdf` files on disk are completely preserved. Zero `Ready_for_Review` projections are dispatched.
5. **Readiness Never Implies Approval (Human Approval Isolation)**:
   - Delivering files and projecting `Status__c = 'Ready_for_Review'` strictly does NOT approve documents or submit applications.
   - All delivered artifacts remain strictly `DocumentApproval.DRAFT`. `ensure_draft_approval_status` enforces this invariant across deliberate regenerations.
6. **Deliberate Regeneration Lineage**:
   - A subsequent generation referencing `predecessor_request_id` validates predecessor existence within the same org, prohibits self-loops/cycles, and isolates fresh draft artifacts from prior versions.
7. **Statutory Semantic Limits Notice & Review Warnings**:
   - The review projection embeds warnings accumulated during validation (GEN-04) alongside the statutory notice:
     `"Draft generated by automated pipeline. Review claims, dates, and subjective phrasing before formal approval or job submission."`
8. **SF-08 Notification Flow Boundary**:
   - Verification of Salesforce Flow notification dispatch (triggering candidate notifications upon `Ready_for_Review`) belongs to external Salesforce Flow architecture (SF-08) and is explicitly documented as PENDING external deployment.

## 4. Recovery Behavior Matrix

| Failure Mode | Detection / Marker State | System Action | Request State | Artifact & Disk State |
|---|---|---|---|---|
| **Process crash before physical send** | `delivery_intents` row in state `pending`. Salesforce has no matching marker. | Query Salesforce by marker (`PROVEN_ABSENT`); execute clean single upload. | Resumes in `upload_pending` -> advances to `ready_for_review` upon completion. | Local files intact; intent updated. |
| **Lost successful upload response** | Remote `ContentVersion` exists; local status is `pending` or missing. | Marker query returns `EXACT_MATCH`; ContentVersion adopted without re-uploading bytes (0 replay calls). | Advances to linking, accessibility check, then `ready_for_review`. | Local file preserved; duplicate Salesforce versions avoided. |
| **Conflicting remote marker match** | Multiple `ContentVersion` records found matching marker. | Marker query returns `CONFLICT`; flags `ErrorCategory.DATA_CORRUPTION`. | Fails gracefully; blocks request in `upload_pending`. | Local files preserved; logged for administrator audit. |
| **Salesforce storage quota failure** | REST response code `STORAGE_LIMIT_EXCEEDED`. | Gateway classifies as `ErrorCategory.CAPACITY`. Delivery halts immediately. | Request remains strictly in `upload_pending`. | Local physical files completely preserved on disk. Zero Ready projections sent. |
| **Salesforce rate limit exhaustion** | REST response code `REQUEST_LIMIT_EXCEEDED` (HTTP 429). | Gateway classifies as `ErrorCategory.RATE_LIMIT`; applies exponential backoff with jitter up to budget ceiling. | Preserved in `upload_pending` until budget window clears. | Files preserved; retry budget strictly bounded. |
| **Missing permissions / linking denial** | REST response code `INSUFFICIENT_ACCESS` (HTTP 403). | Gateway classifies as `ErrorCategory.PERMISSION`. Halts with clear actionable error. | Preserved in `upload_pending`. | Files preserved; prevents corrupt partial delivery. |
| **Inaccessible link / restrictive sharing** | Accessibility gate finds `Visibility != 'AllUsers'` or `ShareType NOT IN ('V', 'C', 'I')`. | `verify_candidate_access` returns `is_accessible=False`. Gating blocks completion. | Blocked from advancing to `ready_for_review`. | Local files preserved; remote links flagged for remediation. |
| **Deliberate regeneration requested** | Request carries `predecessor_request_id`. | Validates predecessor request exists in same org; enforces fresh draft status. | Proceeds through delivery stages under new version ID. | Predecessor files unchanged; new version delivered with draft status. |

## 6. Separate Live Salesforce & Windows Verification Results

### 1. Windows Native Verification

- **Path Sanitization in `CreateContentVersionRequest`**:
  * Salesforce Files treats `PathOnClient` as a simple filename (e.g. `Bewerbung_Maximilian_Müller.docx`).
  * Direct inclusion of Windows backslashes (`\`) or absolute drive letters (`C:\...`) is strictly rejected by contract validation on `CreateContentVersionRequest` to avoid malformed remote metadata.
  * Local files residing in deeply nested Windows directories containing spaces, parentheses, and German umlauts (`C:\Bewerbung München (Entwurf)\...`) are read correctly via binary streaming.
- **Process & Storage Atomicity**:
  * Subprocess crash recovery verified using SQLite WAL mode in `tests/generation/delivery/test_windows_restart.py`.
  * Multi-table SQLite commits (`commit_format_delivery`) run within unified transactions (`with transaction(self.conn)`), guaranteeing that uncommitted uploads leave no phantom mappings upon unexpected Windows process termination.

### 2. Live Salesforce Verification & External Boundaries

- **Salesforce Files REST API Gateway**:
  * Implemented in `src/job_automation/salesforce/files_gateway.py`.
  * Verified wire format serialization (SOQL queries and POST payloads), base64 file chunking, response header parsing, and `ClassifiedError` translation across capacity, rate-limit, and permission faults.
  * Non-replayable mutation guard ensures uncertain HTTP transport errors trigger marker reconciliation rather than repeated duplicate creation.
- **External SF-08 Notification Flow Boundary (Explicitly Marked PENDING)**:
  * In the broader end-to-end architecture, setting `Generation_Request__c.Status__c = 'Ready_for_Review'` triggers an active Salesforce Flow (owned by `SF-08`) that generates in-app notifications and emails for the candidate.
  * In accordance with blueprint instructions: **"Use authorized project-owned records for available live checks; mark SF-08 notification verification pending if unavailable."**
  * Because live SF-08 Flow metadata and notification types are deployed in a later story, verification of candidate email and in-app notifications is formally marked as **PENDING EXTERNAL SF-08 DEPLOYMENT**.
