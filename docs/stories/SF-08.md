## Objective and inspected baseline

Notify the configured candidate when a complete delivered draft is accessible for review, or when a generation request needs action. Repeated updates, delivery reconciliation, status re-entry, and notification retries must not repeat the same readiness alert. Readiness remains distinct from human approval and application progress.

## Event and delivery contract

### Eligibility and transition semantics

| Observed condition | SF-08 behavior |
|---|---|
| `Pending` / `Running`, including an offline worker | No ready or failure alert merely for waiting. Keep request inspectable. No invented timeout failure. |
| `Upload_Pending`, partial delivery, missing/invalid receipt, missing link, wrong org/request/version or unverified recipient access | No readiness alert, even when one file or a nonempty result reference exists. Preserve artifacts and delivery recovery. |
| Current `Ready_for_Review` plus authoritative complete DOCX/PDF set, exact bindings, satisfied completion fields and recipient access | Admit one ready event for that immutable delivered set; dispatch once per configured recipient and channel. Text says draft ready for review, never approved or submitted. |
| `Failed` plus a current committed terminal/actionable failure episode and readable request | Admit one failure event for the episode. No artifact is required. Unknown failure reason uses a safe generic template. |
| `Upload_Pending` plus explicit persisted intervention-required delivery failure, such as capacity/permission failure or exhausted retry budget | May admit an action-required failure event with upload-blocked wording. Remain `Upload_Pending`; never imply that files are ready or discard local output. Without that upstream signal, status/error text alone is insufficient. |
| Recoverable transient retry while retry budget remains | No failure alert per attempt. GEN owns retry classification/backoff. |
| Approval, supersession, warning/notes edits, page refresh, link repair or unchanged projection replay | No new readiness identity. Re-evaluate an unsent blocked alert if appropriate; never reopen an accepted one. |
| Genuine new registered set/version or deliberate new request | Separate ready identity after all gates pass, even when bytes equal an older artifact. New request approval remains independent. |

Readiness means all advertised files are accessible to the actual recipient, including the request/review route and exact versions. Confirm ContentVersion membership, request/set identity, hash bindings, required links and sharing policy. Resolve the complete active set explicitly; never combine DOCX from set A with PDF from set B. Access evidence must name recipient, policy/version and verification time; worker/admin visibility, `AllUsers`, receipt presence or a UI Boolean are insufficient. Reject mock proof in production. Revalidate immediately before send; if verification is unavailable or stale, block dispatch. Later revocation cannot be prevented indefinitely: record verification time and let SF-07 display current unavailability without rewriting history.

### Proposed `SF08RequestNotificationEventV1`

Freeze serialization and API names in S01; this is an additive integration envelope, not a silent reinterpretation of C13/C14 or an existing deployed schema.

- Common: schema version, actual org identity, local request UUID and mapped Salesforce request ID, event kind (`ready` or `action_required`), stable source event key, occurrence UTC time, monotonic source projection revision, current-state reference and payload fingerprint. Derive the route from the validated request ID.
- Ready: immutable set ID/version; sorted nonempty required formats; exact per-format review binding, artifact ID/version, hash, ContentDocument/ContentVersion IDs; registration acknowledgment and verifiable recipient-access evidence.
- Failure: durable failure episode ID, terminal/intervention-required classification, allowlisted reason/action code, and source revision. No free-form diagnostic body, prompt, profile, local path, token or raw exception.
- Output: `admitted`, `replayed`, `blocked`, `stale` or `conflict`, stable ledger reference and safe reason code. Admission is not notification acceptance, and acceptance is not proof that the candidate read it.

**Ready key:** versioned canonical identity over `(origin org, local request UUID, set ID, set version, sorted required-format artifact IDs/versions/hashes and exact remote bindings)`. GEN-06 persists this once; SF-07 validates and exposes it; SF-08 consumes it. Hash only immutable canonical identity, never receipt UUID, verification timestamp, status timestamp, approval revision, retry count or serialized receipt hash. Preserve original identity through restore with explicit verified remote remappings. A binding conflict is quarantined, not assigned a fresh key to evade deduplication.

The existing `ready:<request_id>:<set_version>:<set_hash>` declaration may be retained only with an agreed canonical immutable `set_hash` definition and durable owner implementation. Do not use the coordinator's timestamp marker or a newly generated `transition_id` as the deduplication key.

**Failure key:** `(origin org, request UUID, failure episode ID)`. GEN-01 creates/persists the episode on entry to terminal failure or intervention-required delivery blockage; retries, wording/category corrections and repeated `Failed` projections preserve it. A genuinely resolved episode followed by a new actionable failure needs a new explicit upstream episode. `Failed → Running → Failed` caused by replay or stale writes does not create one. Current metadata lacks this distinction, so failure episode publication is an owner-assigned prerequisite. Do not derive it from raw error text or time.

**Alert key:** SHA-256 of a versioned canonical tuple `(source event key, recipient User ID, channel)`, stored as unique External ID together with its canonical identity/fingerprint for conflict checking. Initial channel is Salesforce custom notification. Template/config version is audit data, not a reason to resend. One complete set produces one ready alert, not one per format.

| Asset | Purpose |

Verify source-format suffix during implementation. |

| `flows/JA_Request_Notification_Dispatch.flow-meta.xml` | Post-commit orchestration for admitted work through the guarded dispatcher. All entry paths share the ledger and the same eligibility checks. |

| `objects/JA_Request_Notification__c/` | Private compact alert/outbox ledger with restrict-delete request reference, immutable unique alert key and source identity, event kind/set or episode reference, recipient/channel/config snapshot, payload fingerprint, state, attempts, next retry, attempt identity, UTC audit times, safe error code and acceptance/uncertainty evidence. Never store document bytes or sensitive diagnostics. |
| `objects/JA_Notification_Config__c/` | Proposed private singleton per org: enabled switch, explicit candidate User lookup, permitted event kinds, language (`de/en`), mobile option, retry bounds and activation watermark. Admin-controlled org data; no real recipient IDs committed in source. Missing/duplicate configuration fails closed. |
| Scoped administrator/recovery permission and custom labels/translations | Admin-only config/recovery entry; service-only ledger writes. Candidate can inspect safe delivery status via an authorized view without Edit/Delete. No broad profile or worker send grant. |

Salesforce supports Flow custom notifications in the desktop bell/mobile app and takes a recipient collection and notification type. Validate exact action inputs, permissions and limits against API 60.0 and the target org before implementing the dispatcher. See the official [Flow custom notification example](https://help.salesforce.com/s/articleView?id=platform.automate_flow_build_example_send_custom_notification.htm&language=en_US&type=5) and [Send Notification action reference](https://help.salesforce.com/s/articleView?id=sf.flow_ref_elements_actions_sendnotification.htm&language=en_US&type=5). These references do not establish atomic, exactly-once delivery with custom ledger DML.

Recipient default: one explicitly configured active internal candidate User in the existing org. Do not infer the candidate from `LastModifiedById`, the worker/Flow execution user, queue ownership, or an email address. Validate request, review and Files entitlement independently for the configured user. No fallback to admin, record owner or a group when resolution fails. Snapshot the recipient at admission. If configuration changes before dispatch, hold old pending work for explicit reconciliation; do not silently redirect it. A configuration change or added recipient does not replay accepted history. Disabled notifications retain durable dispositions; resuming requires a bounded backlog preview and current eligibility checks, not a mass update of requests.

**Durable lifecycle:** `Pending`, `Blocked`, `Dispatching`, `Accepted`, `Retry_Wait`, `Uncertain`, `Suppressed`, `Dead_Letter`. These are ledger states, not new request status values.

1. On relevant source changes, validate envelope/ownership and current source revision. Acquire locks in an order compatible with SF-06/07 (Job, request, notification rows in stable order); insert the unique alert key atomically. Concurrent duplicate insert resolves to existing identity. Same key/different immutable payload conflicts. Rollback cannot leave an orphan send task.
2. Commit admission before attempting a notification. A post-commit dispatcher re-reads current request/set/episode, configuration, recipient and access. Registration may precede or follow the ready projection: a registration-completion signal or bounded reconciliation of blocked candidates must re-evaluate the same event without requiring status toggles. Plain `ISCHANGED(Status__c)` is only a wake-up optimization, never deduplication authority.
3. Under a serialized dispatch claim, persist attempt identity and recovery evidence. Only one sender may own an alert. An accepted key stays accepted through all future updates, including `Ready → Upload_Pending → Ready`, approval, Flow redeployment and worker restart. Never clear history when a request leaves Ready.
4. Record `Accepted` only after confirmed platform acceptance; do not call it delivered/read. Prove send/ledger transaction and rollback behavior in S01/S05. Do not assume a successful send can be rolled back with later DML or safely retried after a lost acknowledgment.
5. If the platform cannot atomically couple acceptance to the receipt, require a durable pre-send fence and one-attempt ownership protocol. A crash/timeout after possible send becomes `Uncertain`, including an abandoned `Dispatching` claim. No automatic resend or lease-expiry takeover may cross that uncertainty. Resolve to accepted or retry only with evidence of acceptance or proven non-send; otherwise retain an operator-visible unresolved item. Document possible missed alerts rather than promising exactly-once network delivery. If this fence cannot be demonstrated in Salesforce, activation remains blocked.
6. Retry only failures proven to precede acceptance, with the same alert key and bounded backoff (proposed three retries after the initial attempt, configurable delays of 1, 5 and 30 minutes, respecting platform retry advice). Lock contention before send does not consume a send attempt. Permission/configuration/access issues block until repaired. Exhaustion becomes `Dead_Letter`. Repair/recovery never resets an accepted/uncertain key to pending blindly.
7. Before delayed send, suppress obsolete failure episodes resolved by later authoritative progress and ready events replaced by a different current set. A temporary access loss can block an unsent current ready event and later release that same key. Old projections cannot resurrect obsolete events. Log safe counts/reasons for support; notification faults never recursively produce candidate failure notifications or roll back successful generation/delivery.

Use a bounded Salesforce queue/recovery entry, with an admin preview/retry operation as a minimum. Any timed recovery is restricted to this ledger, explicitly packaged and limit-tested; no Windows service, model call, polling of localhost or Phase 2 scheduler is introduced.

## Safe notification content and navigation

Use fixed localized templates with validated request auto-number only. Avoid employer/title, candidate names, job text and free-form warnings on notification surfaces. Proposed English examples:

| Kind | Title | Body / action |
|---|---|---|
| Ready | `Draft ready for review` | `Request {requestNumber}: DOCX and PDF drafts are available. Open the request to review them.` |
| Terminal failure | `Draft request needs attention` | `Request {requestNumber} could not complete. Open the request for the next step.` |
| Delivery intervention | `Draft delivery needs attention` | `Request {requestNumber}: file delivery is blocked. Open the request for the next step.` |

Provide equivalent reviewed German labels. Document language is not assumed to be notification language; use configured candidate UI preference with a defined fallback. Store UTC audit times and display Europe/Berlin where shown.

Target the validated `Generation_Request__c.Id` through a supported record target. The SF-07 request page must expose the exact advertised set/versions, including history if a newer set arrives before the alert is opened. The link never approves, regenerates or marks Applied. Use authenticated org navigation, no public distribution URL, client-supplied route, generic `salesforce.com`, local file path or diagnostic reference. Failure links must work without any file and while the local worker is offline.

No alert body, title, target parameters or ledger error text may contain `Error_Message__c`, raw `Error_Reason__c`, `Error_Ref__c`, `Local_Artifact_Ref__c`, `$Flow.FaultMessage`, stack traces, OAuth material, prompts, profile facts or document excerpts. Map allowlisted codes to next steps on the request. `job_unavailable` directs the candidate to inspect the request and, if desired, use SF-06's explicit new-request/override confirmation; it never supplies consent automatically. Request-level safety is a separate SF-05/GEN-01/SF-07 gate, not solved by sanitizing the bell alone.

## SF-08-S03 — Admit readiness and actionable failures from Flows

**Objective:** convert authoritative request events into durable eligible alert work.  
**Dependencies:** S01–S02, implemented SF-07 access/event contract and GEN-01/06 publications.  
**Inputs → outputs:** committed transitions and registration-completion signals → admitted/replayed/blocked/stale/conflict ledger outcomes.  
**Owned metadata:** observer Flow, admission invocable/service and minimal agreed event-consumer wiring.

Tasks:

1. Implement the eligibility table; creation directly in Ready/Failed is subject to the same complete evidence and activation watermark rules as updates. Unknown schema/state fails closed.
2. Join the exact registered set and access evidence; require both formats and current recipient entitlement. Never use a nonempty result reference, registration row count or `allFormatsDelivered` alone.
3. Handle repeated updates and both registration/projection arrival orders with unique-key admission. Bulkify reads/writes; coalesce duplicate work and use consistent lock ordering.
4. Admit terminal and explicit upload-intervention episodes, excluding transient attempts/offline waiting. Reject untrusted/raw diagnostics; do not synthesize a new episode for each error edit.

Acceptance: a complete accessible current set admits one ready alert; DOCX-only, stale receipts, wrong target, synthetic proof and Upload_Pending admit none. Failure admission requires a readable request, not a delivered artifact. Duplicate and concurrent observers return the same alert.

Deployment impact: inactive Flow plus service and owner-agreed minimal wiring; no processing-field, file, approval or Job edits by SF-08.

## SF-08-S04 — Dispatch safely and recover without duplicate alerts

**Objective:** deliver admitted alerts through one durable dispatcher and make every ambiguous outcome inspectable.  
**Dependencies:** S01 platform proof, S02–S03, SF-02 and SF-07 recipient-access validation.  
**Inputs → outputs:** committed ledger work → Accepted, Blocked, Retry_Wait, Suppressed, Uncertain or Dead_Letter.  
**Owned metadata:** dispatch Flow, guarded Apex adapter/queue/recovery entry and safe operational view.

Tasks:

1. Implement the lifecycle, serialized claim, pre-send revalidation and proven send/receipt protocol. Replays and stale async continuations must consult durable identity before any send.
2. Implement fixed de/en content, record target and one recipient per ledger item. Enforce current body/title limits without truncating arbitrary diagnostic text into an alert.
3. Add bounded retry only for proven non-send, due-work recovery, kill switch, safe failure codes and operator reconciliation of uncertain outcomes. Never send notification-failure notifications recursively.
4. Suppress stale failure/ready work at dispatch; leave request processing and approval untouched. Keep accepted and uncertain history through config changes and deployments.

Acceptance: one accepted ready alert survives status cycling, replay and restart without another send. A send-success/receipt-loss simulation becomes reconcilable uncertainty, never an automatic repeat. Broken recipient access blocks sending. Notification failure does not undo delivered files or change request status.

Deployment impact: asynchronous dispatch/recovery capacity and scoped execution permissions. No external channel, paid dependency, worker startup or model runtime change.
