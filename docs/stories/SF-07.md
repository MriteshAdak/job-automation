## Objective and inspected baseline

Let the candidate inspect durable request progress, open the exact delivered DOCX/PDF draft, review warnings, approve a specific artifact version, identify the approved version later, and deliberately request another draft. Delivery, human approval and application progress remain independent. Preserve original and successor files, request lineage and approval history.

## State and version rules

These rules are required by the blueprint/user. Object names and the specific transaction/UI design below are **proposed engineering choices** to finalize in S01.

| Processing / delivery | Human approval | Candidate display and allowed behavior |
|---|---|---|
| `Pending` | No new artifact approval | “Queued — waiting for the local worker.” Inspect options/history; no invented ETA, queue position or heartbeat. |
| `Running` | No new artifact approval | “Generating.” Show persisted claim/frozen inputs, not fabricated percentage completion. |
| `Upload_Pending`; local-only, partial upload, uncertain acknowledgment or failed link/access check | `draft` for any new artifact | “Upload pending — draft is not yet ready for review.” Show concise reason and last recorded update. No approval or ready announcement. A partial file may appear in Files, but must not be advertised as the completed review set. |
| `Ready_for_Review` plus complete verified delivery registration and current candidate access | `draft` | “Delivered — ready for review.” Offer exact-version open/download, warnings and explicit approval. Readiness is not approval. |
| Same delivered request | `approved` for an exact version | “Approved,” with format, request, artifact/set version, ContentVersion identifier, approver and UTC event time displayed in Europe/Berlin. Request state remains `Ready_for_Review`. |
| Same delivered request / historical version | `superseded` | “Superseded,” replacement/version link and historical decisions retained. A previously approved version also shows when/by whom it was approved. Superseded does not mean deleted. |
| `Failed` | Preserve earlier artifacts/decisions, if any | Show safe failure and request history. A new attempt uses SF-06's explicit new-request route; worker delivery recovery remains GEN-owned. |
| Previously ready/approved but file removed, access revoked, receipt invalid or mapping unavailable | Preserve recorded approval; access is currently unverified/unavailable | Display historical processing/approval separately from “File unavailable” or “Delivery verification incomplete.” Disable new approval and false ready affordances. Do not silently rewrite history or select another/latest file. |

Do not add `Approved` or `Superseded` to `Generation_Request__c.Status__c`. Review actions never write request processing state or Job application progress. Unknown schema/state values show a compatibility issue and disable mutations; they do not default to ready.

Approval binds to `(org_id, request_id, artifact_id, artifact_version, format, content_hash, ContentDocumentId, ContentVersionId)` within an immutable artifact-set ID/version. UUIDs, Salesforce IDs, local artifact versions and provider VersionNumber labels are separate identities. Titles, timestamps, “latest,” a Job lookup or a ContentDocument ID alone cannot identify approved bytes.

**Proposed approval granularity:** approve one explicitly selected physical format/version at a time. DOCX approval does not approve PDF, even within the same set; a future batch action must enumerate and confirm every exact version atomically. The initial UI must show separate format badges and must not label the whole set approved when only one format is approved. Require the complete declared delivery set before opening approval; required formats come from GEN-05/06 and cannot be reduced by the UI to hide a failed upload.

**Proposed replacement policy:** at most one current approved version per authorized candidate, Job, document type and format. Language/template/context remain visible attributes, not implicit replacement permission. An approval replacing the current version must explicitly identify and confirm the old and new versions, including changed language/options. In the same transaction, approve the new version, supersede the explicitly selected previous approval and retain both events. A stale current-approval selection returns a conflict. Drafts can be explicitly superseded by a delivered successor of the same Job/type/format; that does not approve the successor. Do not infer replacement merely from newer timestamps or request ancestry. No automatic reactivation of a superseded version; generating another draft gives it a new identity.

A queued, delivered or failed regeneration **never** copies an approval or automatically supersedes the previous approved version. Example: request A / PDF v1 is approved; B references A and delivers PDF v1 under a different artifact/request identity. A stays approved; B is draft. Only explicit approval-and-replacement makes B approved and A superseded. A's approval event and exact bytes remain identifiable. An independently uploaded newer ContentVersion likewise receives no approval from its document's older version.

## Salesforce contracts and proposed metadata

Use compact companion records rather than a mutable “Approved” flag on Job/request or ContentDocument. Proposed API names are collision-checkable choices, not existing assets:

| Record / boundary | Required contents and ownership |
|---|---|
| `JA_Artifact_Review__c` | One immutable binding per artifact/version/format, unique version key, contract version, org/local request UUID and restrict-delete request lookup; artifact/set IDs and integer versions, format, SHA-256, size, exact ContentDocument/ContentVersion IDs, marker, delivery receipt/readiness references, delivered-at, safe warnings/notice and predecessor binding. Worker registration creates delivery data only. Candidate reads it; neither candidate nor worker can rebind it. |
| Review projection on that record | `draft/approved/superseded`, review revision, current approval actor/time/event reference and superseded-by reference. Only the controlled SF-07 decision service changes these derived fields. A newly registered version is always draft; replay of registration preserves existing human state. |
| `JA_Artifact_Review_Event__c` | Append-only event ID, principal-scoped submission key, action, exact selected binding, previous/new state, prior review revision, actor and server UTC timestamp; explicit replacement binding and optional bounded candidate note. Approval events retain the complete identity/hash even after later supersession. Restrict-delete relationships; no general edit/delete for candidate or worker. |
| `SF07DeliveryRegistrationV1` (proposed) | GEN-06 receipt + ReviewProjection → validated Salesforce review rows and an acknowledgment of exact immutable bindings. | `SF07ReviewCommandV1` (proposed) | Action `approve`, `approve_and_replace` or `supersede`; selected review ID and exact version/hash, expected review revision/current approval, any explicit replacement, acknowledgment and stable intent token. ### GEN-06 delivery and readiness agreement

1. GEN-06 persists intent and performs upload/reconciliation. Marker grammar remains `gen06:v1:<request_uuid>:<artifact_uuid>:<artifact_version>`. SF-07 supplies the allowed Files fields and permissions. Verify the current Description-based marker/hash encoding is queryable, fits actual field limits and remains immutable for managed versions. If a dedicated ContentVersion field is needed, record exact metadata and an owner-approved migration; never change marker grammar or use request `Operation_Marker__c` as a file marker implicitly.
2. Required target is the exact `Generation_Request__c`. Proposed default is request-only linking; navigate from Job through requests/history. Optional `Job__c` links require an explicit sharing assessment because their audience may be wider. GEN-06 must honor this policy; if a Job link is advertised as required, its failure blocks readiness. Do not treat current ignored optional-link errors as successful delivery to that surface.
3. SF-07 defines the allowed audience and read access; GEN-06 verifies delivery under that policy. An access receipt must identify the intended candidate or a verified, versioned policy resolving that candidate's record/File access. Worker/admin visibility, a link row, `AllUsers`, or a checksum alone is insufficient. `mock_verification` is test-only. Stale/missing evidence blocks integrated readiness until owner resolution; do not fabricate a candidate principal.
4. Register immutable bindings before projecting readiness. Reject missing/duplicate/cross-request formats, wrong org, inconsistent set/version/hash, unbound IDs, unverified access or unsupported schema. Same binding/key replay is idempotent; same key with different bytes/remote IDs is a conflict. Worker replay must never reset approved/superseded to draft. Partial registration is inspectable but not an approval target.
5. GEN-01 remains the single ordered request-state writer. Its ready payload must satisfy SF-05's `Completed_At__c` and `Result_Artifact_Ref__c` validation and refer to the registered complete set. Resolve a backward-compatible primary reference with SF-05/GEN-01 while keeping all format/version rows authoritative. No assumption that `Review_Notes__c` or `Remote_File_Id__c` exists. Lost registration/readiness acknowledgment is reconciled by exact payload/readback, not status alone; delayed upload-pending projection cannot overwrite newer readiness or any approval.
6. Return stable registration/readiness keys for GEN-06 reconciliation and SF-08 notification deduplication. Readiness is a delivery event, separate from approval/review revisions. Refreshing a page, repairing access, replaying registration or approving a version must not create a new delivery event automatically. SF-08 owns actual notification dispatch rules.
7. Salesforce is authoritative for human review. GEN-06 can read/export decision events for an explicitly versioned local cache; it cannot author, reset or infer approval. OPS-01 backs up the event ledger and exact bindings. Define replay/watermark/conflict behavior before reflecting approval into local Artifact records; until then, label local approval as unsynchronized and never use its default draft to overwrite Salesforce.

### File visibility and permission policy

Proposed least-privilege default for the internal candidate is Viewer (`ShareType=V`) on the private request, with `InternalUsers` visibility where supported and verified. GEN-06 currently defaults to AllUsers; adoption therefore requires an explicit compatible setting/adapter change owned by GEN-06. AllUsers is not a public URL but also does not establish candidate entitlement. Do not automatically switch to Collaborator or inferred sharing merely to make a test pass. Inspect all links/ownership/shares, including auto-created links, for unintended access. Salesforce distinguishes the [file-link relationship](https://developer.salesforce.com/docs/platform/field-reference/references/field-reference/salesforce-field-reference-contentdocumentlink.html) and [record-file visibility settings](https://help.salesforce.com/s/articleView?id=000320738&language=en_US&type=1).

| Principal | Allowed | Excluded from project grants |
|---|---|---|
| Candidate reviewer | Read authorized Job/request/review history, open/download exact versions, invoke explicit review commands; regeneration only with SF-06 requester access. Proposed `Job_Document_Reviewer` set and `JA_Review_Generated_Documents` custom permission. | Editing worker fields, rebinding version/hash, directly changing derived review state, deleting ledger/files through this feature, public distribution, broad record access. |
| Worker | Read authorized request/Job; create/reconcile managed Files and links under agreed policy; invoke delivery-registration only; maintain its existing operational fields. | Invoking approval/supersession, writing human notes/events, granting itself reviewer permission or changing candidate tracking. |
| Read-only observer / unrelated user | Only independently authorized record/file reads, if any. | Approval, regeneration, access to private candidate files or IDs through forged review requests. |
| Administrator | Diagnose configuration and perform separately controlled recovery. | Admin success is not proof that candidate/worker least-privilege roles work. |

Permission sets are additive. Inventory the actual effective identity and OAuth scopes; if worker and candidate share one admin identity, role separation cannot be claimed from two sets. Require scoped operational identities already available without a paid dependency, or record that enforcement remains unverified and block a least-privilege sign-off. Keep private requests readable/editable by the intended worker through a narrowly scoped, documented row-sharing arrangement; object Read/Edit alone grants no row access.

Enforce class/custom-permission entry access, record sharing, CRUD and FLS for reads and mutations. At repository API 60.0, use explicit enforcement rather than assumptions from newer API defaults. Any narrow service elevation for protected registration/event storage is limited to fixed fields after caller-role and underlying request/version access checks; no generic elevated DML endpoint. Hidden buttons, read-only layouts and `with sharing` alone do not establish field/object security. See Salesforce's [Apex security guidance](https://developer.salesforce.com/docs/platform/lwc/guide/apex-security.html).

Opening an approved file must resolve the stored ContentVersion ID. Verify the chosen supported navigation/download mechanism serves that version even after another ContentVersion exists. A standard Files tile or document-level preview that opens latest can supplement history but cannot be the authoritative approved-file action. Use authenticated org-relative routes or the configured approved org origin, never generic `salesforce.com`, public ContentDistribution links, local disk paths or client-supplied URLs. No iframe/editor or localhost access is needed.

### Review transaction and history

The review screen shows document type, language, request and set/artifact versions, format, delivery time, frozen input identifiers, safe warnings and the reminder to review claims, dates and subjective phrasing. Validation is not semantic truth. Notes are candidate-owned and rendered as text. Opening/downloading a file records no approval. Acknowledgment must be explicit and unchecked for each fresh intent; presenting a checkbox is not proof the candidate read the bytes.

Proposed atomic command behavior:

1. Authorize the current principal and selected request/version; check principal-scoped intent replay. A known token with changed payload conflicts; replay rechecks current visibility before revealing details.
2. Lock the Job, then relevant review rows in stable ID order, consistently with SF-06's parent-first lock convention. Re-read immutable version bindings, complete delivery/access evidence, current approval and expected review revisions. A server-side uniqueness/concurrency strategy must also cover an initially empty approval set.
3. Reject upload-pending/partial/unverified/inaccessible/mismatched/superseded targets and stale replacement selections. Recheck exact ContentVersion membership in its document and request mapping. Access lost since page load produces no event. If file-access changes cannot be locked with review rows, document and test that platform boundary; retain authorization evidence/time and detect later loss on read rather than promising eternal availability.
4. Persist the event(s), current-state projection and token result in one transaction. Approval-and-replacement is all-or-nothing. Derive actor/time on the server. No edits to GEN processing fields or candidate Job fields.
5. Ambiguous success reuses the same intent token; no duplicate decision event. Contention returns bounded retry with that token. Concurrent incompatible approvals must not both become current. Keep original event identity/time on replay; registration retries and restores cannot change it.

Preserve managed originals. A downloaded DOCX edited locally is a different artifact requiring new bytes/hash/version and fresh review through an agreed GEN-05/06 path; it is not the approved original. Standard/manual Salesforce uploads not registered through the delivery contract appear as untracked files, with no inherited approval or automatic adoption. A general edited-file import workflow is outside SF-07; explain this limit without blocking review of known delivered versions.

## SF-07-S05 — Expose regeneration through SF-06

**Objective:** give review/history a safe route to another draft without duplicating enqueue logic.  
**Dependencies:** S03, implemented SF-06 handoff/shared entry, SF-05 lineage.  
**Inputs → outputs:** selected authorized request/version → SF-06 confirmation → new durable request or existing replay/reuse result.  
**Owned metadata:** review-page regeneration entry/button and adapter to the existing SF-06 entry; enqueue service/receipt ownership remains SF-06.

1. Pass server-validated request predecessor, Job and document type plus suggested language/template/context; never pass approval, frozen inputs, artifact IDs as new identity or arbitrary processing fields.
2. Invoke SF-06's deliberate-regeneration confirmation and stable submission token. A confirmed fresh intent creates a new request; replay of that intent returns the same request. Keep active work and all history intact.
3. Reset unavailable-job consent to false. A `job_unavailable` failure routes through SF-06's explicit override confirmation/new-request logic; no reset-to-Pending shortcut.
4. Show queued/reused/replayed outcomes and link the returned request. Explain that the old approved version remains approved while the new result starts as draft. Cancel creates nothing.
5. Keep the entry disabled with a clear configuration explanation until SF-06's implemented interface is compatible. Do not add direct Create Records as a fallback.

Acceptance: two clicks for one confirmed regeneration create one successor; a separately confirmed intent creates another; no approval is copied, old decisions are unchanged, and generation does not need a running local worker.
