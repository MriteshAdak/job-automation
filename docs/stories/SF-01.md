## Boundary and dependency contracts

SF-01 owns the project-controlled Company/Job metadata, canonical External IDs, Job-to-Company lookup, mapped fields, field descriptions, identity validation rules where compatible, and creation defaults. It produces a reviewed mapping specification, source metadata, migration/deployment plan, validation evidence, and `docs/components/SF-01.md` during implementation.

SF-02 owns OAuth and permission grants; SF-03 owns layouts, views, reports, candidate actions and decision UI; SF-04 owns ongoing capacity/metadata portability; SYNC-01 owns mapping code, outbox ordering, runtime validation, candidate backups and reconciliation. Identify integration changes for those owners without implementing their components here. Generation objects, Files, notification Flows, scheduling, and automatic drafting are excluded.

| Dependency / contract | SF-01 consumption and output obligation |
|---|---|
| SF-00, prerequisite | Inventory and ownership evidence determine actual names and reusable metadata. Carry forward gaps instead of asserting the org is empty. |
| FND-01 C07 `CanonicalJob` / `PostingRevision`, schema 1.0 | Persist stable job/company UUIDs separately from Salesforce IDs. C07 permits an unresolved company; current sync publication does not. Never invent a Company merely to satisfy a lookup. |
| FND-01 C11 `Assessment`, schema 1.0 | Map final disposition, summary reason and optional score/scale. Eligibility is independent of application progress. Full rule/evidence/profile/model provenance stays local. |
| FND-01 C12 `SyncPayload` / `SyncOperation`, schema 1.0 | Receive only the machine projection; preserve null score/scale clearing, source URL collection serialization, UTC evaluation time, operation identity and ordered writes. No candidate fields are added to C12. |
| Current `SyncSubmission`, `SyncWriteStep`, `RemoteEntityMapping` | Company UUID comes from the submission; confirmed Salesforce parent ID fills the lookup. Markers and per-entity sequence numbers are persisted on both objects. Remote mappings remain scoped by org, object and canonical entity. |
| Current `SyncMappingConfig`, schema 1.0 | Publish explicit mappings for every property listed below, actual picklist API values, candidate read/backup allowlist, mapping version/hash, and private target-org binding. Existing configuration supports names, not arbitrary extra required payload fields or per-object marker names. |
| SFCLIENT-01 / SF-02, integration dependencies | Confirm field type/read/create/update capability and authorized worker identity before live tests. SF-01 specifies permission needs; it does not grant them. |
| IDENTITY-01/02, MATCH-01/02, SYNC-01 | Remain authorities for identity, availability, assessment and publication. SF-01 does not recalculate eligibility or infer closure in Salesforce. |

Keep the eight foundation state domains separate. Application progress values are `New`, `Review`, `Shortlisted`, `Applied`, `Interviewing`, `Offer`, `Rejected`, `Withdrawn`, `Archived`. Machine disposition is `eligible/review/rejected`; availability is `active/not_seen/unavailable/unknown`. Similar labels such as `Review` and `Rejected` do not establish a shared state machine.

Changes to a public contract require the blueprint's version/schema/fixture and consumer migration discipline. A configuration-only rename can retain configuration schema 1.0 but must change `mapping_version` and its hash; frozen outbox operations must not silently adopt a new mapping.

## Logical-to-physical mapping proposal

These are **proposed engineering defaults**, not inspected org facts or candidate preferences. Resolve every name against SF-00 before generating deployable members. For a reusable object, preserve compatible existing field types and names rather than converting them to this proposal.

### Company and Job identity and relationships

| Logical value / config property | Conditional physical mapping | Proposed metadata and behavior |
|---|---|---|
| Company / `company_object` | `Company__c` | Reuse only with compatible semantics and confirmed ownership; otherwise consider the alternatives below. |
| Company UUID / `company_external_id_field` | `Canonical_Company_Id__c` | Text(36), External ID **and Unique**, case-insensitive uniqueness; lowercase hyphenated UUID from `str(uuid.UUID)`. No generated/default company ID in Salesforce. |
| Employer name / `company_name_field` | Existing compatible `Name`; for a new object, `Company_Name__c` | New-object proposal: Text(255) business name and an autonumber `Name` (`CMP-{000000}`). This avoids a second required name write and gives the business name an explicit capacity. Current example maps to `Name`; update the mapping explicitly if this proposal is selected. |
| Job / `job_object` | `Job__c` | One record per canonical job, not per source posting or revision. |
| Job UUID / `job_external_id_field` | `Canonical_Job_Id__c` | Text(36), External ID **and Unique**, same UUID rules as Company. Independent unique indexes on the two entities. |
| Job title / `title_field` | Existing compatible `Name`; for a new object, `Job_Title__c` | New-object proposal: Text(255) title and autonumber `Name` (`JOB-{000000}`). Never write the business title to an autonumber field. Longer input is a visible validation failure pending a supported projection; do not silently truncate. |
| Parent / `job_company_lookup_field` | Job.`Company__c` → selected Company object | Many Jobs to one Company, ordinary Lookup, proposed child relationship name `Jobs` after collision inspection. No master-detail/cascade-delete behavior. For new dedicated objects, require a Company and restrict deletion while referenced. |
| Salesforce record IDs | Platform `Id` and local remote mappings | Never replace canonical UUIDs with 15/18-character Salesforce IDs. A Job lookup contains the acknowledged Salesforce Company ID, not the UUID string or company name. |

For new dedicated objects, canonical ID and business name/title are required. Add field-specific validation for canonical UUID syntax and prevent changing a nonblank canonical ID through normal edits. The correction path is a separately reviewed identity/migration procedure. For reused objects, do not impose global required/immutability rules on unrelated legacy records; use a demonstrably compatible project scope or choose dedicated objects. Nullable legacy IDs are not eligible for automatic adoption until the backfill is reviewed.

Two source postings for the same canonical job share its External ID. Title/name/description changes, content hashes, source IDs, URLs, evaluation IDs and sync markers cannot become permanent canonical keys. A genuine repost/new requisition may have a new UUID; SF-01 does not decide merges or splits.

### Machine-owned mapped fields

| Entity | Config property → proposed field | Type / values / null and update behavior |
|---|---|---|
| Job | `availability_field` → `Availability__c` | Restricted picklist: local `active` → `Active`, `not_seen` → `Not Seen`, `unavailable` → `Unavailable`, `unknown` → `Unknown`. Never default a missing observation to Active. |
| Job | `disposition_field` → `Assessment_Disposition__c` | Restricted picklist: `eligible` → `Eligible`, `review` → `Review`, `rejected` → `Rejected`. No default Eligible or candidate approval inference. |
| Job | `reason_field` → `Assessment_Reasons__c` | Plain Long Text Area(32768), compact C11 summary. Machine replacement is allowed; it must never target candidate notes. |
| Job | `score_field` → `Relevance_Score__c` | Nullable Number(18,6), proposed finite nonnegative score representation. No default 0, percent conversion or probability label. SF-01 does not impose a universal 0–100 scale on C11. |
| Job | `score_scale_field` → `Score_Scale__c` | Nullable Text(255), supplied scale declaration. Explicit null clears the old scale when the score becomes absent. |
| Job | `last_evaluated_field` → `Last_Evaluated_At__c` | DateTime, source `evaluated_at` serialized with UTC offset. Preserve assessment event time on replay; do not replace with Salesforce save time. |
| Job | `source_urls_field` → `Source_URLs__c` | Nullable plain Long Text Area(32768). Current mapper joins `source_urls` with newline; empty collection becomes null to clear the old projection. Preserve multiple URLs; not a single URL field. |
| Company and Job | `sync_marker_field` → `Sync_Operation_Marker__c` | Text(255), nullable for unmigrated legacy rows, no default. Stores the full opaque marker (currently `sync-comp-…` / `sync-job-…`); not a UUID-only field, identity key or candidate decision. |
| Company and Job | `sync_version_field` → `Machine_Sync_Version__c` | Number(18,0), no default. Positive monotonic integer per entity, exact readback and bounded capacity; must not round or reset on later updates. |

The UUID, Company relationship, employer name and title above are also machine-owned. Marker/version API names must be the same on both objects with current configuration. If the org needs different names per object, that is a SYNC-01 configuration/consumer change, not an undocumented SF-01 workaround.

For new dedicated records, disposition, availability, evaluation time, marker and version must be supplied by integration; validate their presence without fabricating values. For reuse, stage compatible validation only after legacy analysis. Score/scale and source URLs remain nullable. The current Python contracts do not cap every text length, numeric precision or sequence range: record these as runtime validation dependencies for SYNC-01 and test their boundaries before live enablement. Numeric quantization, if needed, must be an explicit versioned projection decision; no silent rounding. Missing/unsupported picklist keys must fail clearly instead of relying on the mapper's current fallback to the raw enum string.

Only this compact projection is required now. C06 location, workplace restrictions, compensation, description and source dates; C07 revisions, first/last seen and application URL history; and detailed C11 evidence remain local. `source_urls` is not an application-URL field. Do not create unmapped fields and claim they are populated. Any later Salesforce projection of those facts needs an explicit contract/mapping change, provenance and capacity decision.

### Candidate-owned fields and creation defaults

| Proposed Job field | Proposed metadata | Creation default | Authority after creation |
|---|---|---|---|
| `Application_Progress__c` | Restricted picklist with the nine foundation progress values; preserve compatible existing API labels through a documented mapping | `New` when omitted on insert | Candidate; never derived again from eligibility or availability |
| `Candidate_Notes__c` | Nullable plain Long Text Area(32768) | Blank | Candidate, including intentional clearing |
| `Candidate_Decision__c` | Nullable Text(255) for the initial compact decision/override record | Blank; no assumed approval/override | Candidate; existing richer decision fields may be reused if compatible |
| `Follow_Up_Date__c` | Nullable Date | Blank; no invented deadline | Candidate; retain date-only precision |
| `Interview_Date__c` | Nullable Date in the new-object proposal | Blank | Candidate; an existing compatible DateTime field may be retained with its type documented rather than losing precision |

All five names, or their actual mapped alternatives, belong in `candidate_fields` for read/backup and outbound exclusion. Include any additional discovered candidate-owned fields that need protection and backup. A decision does not rewrite C11 disposition, authorize an application, or enqueue a generation request.

**Defaulting contract:** prefer the `Application_Progress__c` field's creation default `New`, with no status-maintenance Flow. Both initially eligible and initially reviewable jobs start New; reviewability is independently visible through `Assessment_Disposition__c = Review` for SF-03. This is an explicit proposed default, not an asserted user workflow preference. Inspect record-type defaults and test the API insertion path, not just a UI default.

Candidate fields are absent from **all** sync requests, including initial inserts, updates, retry payloads, reconciliation repairs and restores performed through ordinary sync. The client never sends `Application_Progress__c = New`. Defaults must apply when Salesforce creates the record, not when an application merely believes an upsert will insert. Supplied candidate progress on an authorized insert, such as Applied, must survive. Distinguish an omitted field from an explicit null; document/test the org's insert behavior. An intentionally cleared field on an existing record stays clear.

If compatible reuse needs a conditional creation default that field metadata cannot express, use only a project-owned, **create-only before-save** Flow, scoped to the project and guarded by an empty target field. It must have no update trigger, scheduled path, secondary record update or notification. Prefer the simple field default unless evidence requires this exception. Never implement a create-or-update rule that fills blanks: a later candidate clear is also a blank. Inspect existing Flows, Apex, workflow/process rules, record types and validation rules for indirect resets; excluding fields from Python payloads alone cannot prove preservation.

Salesforce distinguishes External ID matching from uniqueness; both flags are required here. See [Custom Field Attributes](https://help.salesforce.com/s/articleView?id=platform.custom_field_attributes.htm&language=en_US&type=5). The fallback Flow proposal follows Salesforce's separate [record creation/change trigger options](https://help.salesforce.com/s/articleView?id=platform.automate_flow_build_get_started_record_triggered_start_with_record_change.htm&language=en_US&type=5). These platform references were checked during planning; they do not establish the target org's configuration.

### Alternative mappings and compatibility decisions

| Inspection result | Mapping decision and constraints |
|---|---|
| Compatible, demonstrably project-owned `Company__c` / `Job__c` | Reuse exact names and compatible fields. Map text `Name` only if writable and its measured length is adequate. Preserve existing autonumber `Name` and map a writable business-name/title field instead. Never convert Name type in place merely to match an example. |
| Default object names authoritatively absent | New `Company__c` / `Job__c` may use the new-object proposal above, subject to capacity and ownership gates. Name availability must be rechecked before deployment. |
| Default names are unrelated, shared, managed or incompatible | Protect existing metadata. Proposed distinct names: `JA_Company__c` and `JA_Job__c`; map `company_object`, `job_object` and the Job lookup target explicitly. These are examples, not reserved names. Field/relationship names also need collision checks. |
| Existing Account or another employer object is proposed for reuse | Consider `company_object = Account` (or exact inspected API name) only if semantics, record scope and authorized ownership are proven. Shared Account.Name is not automatically machine-owned. A dedicated writable name projection may need `company_name_field` plus handling of the object's other required fields; current mapping cannot supply arbitrary extra fields. Treat that as a blocker/consumer change or use a dedicated Company object. |
| Compatible namespaced object/fields | Use exact qualified API names and confirmed writable extension fields. Respect package ownership; do not replace managed members. A nonmodifiable External ID or unsuitable relationship blocks reuse. |
| Existing `Status__c` mixes candidate application state and eligibility | Preserve it as candidate-owned if that is its established meaning. Add/map a separate machine disposition field. Never map both state domains to it or reinterpret historical values. |
| Existing title/name is formula/autonumber, too short, or candidate-owned | Choose a writable machine field and map it. An existing text Name that is still required on insert cannot be bypassed just by adding another field; provide a compatible creation solution or declare the object incompatible. |
| Existing required field, record type, dependent picklist or automation needs extra payload | Inventory the exact requirement. Current mapping has no `RecordTypeId` or generic additional-field map. Use a proven compatible existing default or hand the required consumer change to SYNC-01; no hidden hardcoded field injection. |
| Different API picklist values but identical semantics | Populate `disposition_mapping` and `availability_mapping` with active values permitted for the worker's effective record type. Do not change shared value sets or unrelated values. Candidate progress mapping/default must be documented separately. |
| Visibility, ownership or semantics unresolved | Leave the affected physical mapping unresolved. No deployable member may overwrite the unknown asset. |

Each final mapping row must record logical value, exact object/field, type/length/precision, null/default rules, ownership, effective access, record-type applicability, evidence source/date, compatibility result, migration need and responsible owner. Full [sObject Describe](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-sobject-describe.html) plus scoped metadata/automation evidence is the inspection basis; a successful typed describe alone is insufficient.
