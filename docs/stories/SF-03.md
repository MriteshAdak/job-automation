# SF-03 — Tracking views and candidate decisions

Component: **SF-03**  
Status: **PLANNED — stories only; no metadata authored or deployed**

Requirement: **R08**; respect R14/R15/R16 platform, privacy, and recovery constraints  
Planning date: **1 November 2026**  
Baseline: [IMPLEMENTATION_BLUEPRINT.md](../../IMPLEMENTATION_BLUEPRINT.md), especially §§4–8

## Objective and scope

Give the candidate a Salesforce workspace for finding eligible jobs, reviewing unresolved eligibility/assessment, shortlisting opportunities, tracking applications, and managing follow-ups. The candidate can edit application progress, notes, decisions/overrides, and dates while seeing the current machine assessment and source availability separately. Later ingestion must preserve those edits, including deliberate blanks.

This document plans SF-03 only. It does not implement or deploy metadata, change synchronization, select an org, provision credentials, or create records. Proposed names, queue conventions, and layout choices below are engineering defaults for implementation, not additional user requirements or verified live-org facts.

Out of scope: changes to eligibility rules, source facts, C11 results, publication policy, canonical identity, worker authorization, backup implementation, a separate dashboard application, new Application/Shortlist objects, application submission, generation actions/requests, document approval, notifications, reminders, and scheduled runs. Phase 1 and Phase 2 remain with their catalog owners.

## Candidate experience contract

### Separate the three state domains

Use distinct headings and explicit field labels: **Your application**, **Machine assessment**, and **Posting availability/source**. Avoid a generic “Status” label. `Application_Progress__c=Review` means the candidate's workflow stage; `Assessment_Disposition__c=Review` means machine review is needed. Likewise candidate `Rejected` and machine `Rejected` have different meanings.

The candidate can write “Proceed despite uncertainty; confirm with recruiter” into `Candidate_Decision__c`, add detail to notes, and shortlist/apply. This records their intended action. It does **not** rewrite source facts, approved candidate evidence, hard-rule outcomes, C11/model results, scores, reasons, availability, or publication eligibility. It does not authorize generation for an unavailable job. A correction to underlying facts requires the relevant upstream owner and a later reassessment.

### Unknown eligibility and missing assessment

- Route `Assessment_Disposition__c=Review` to a dedicated **Review Jobs — Unknown Eligibility / Assessment** queue. Show the literal machine disposition alongside candidate progress and availability in every tracking surface.
- On a Review record, display prominent text: **“Review required: eligibility or assessment is unresolved. Read the machine reasons. Unknown is neither a pass nor a rejection.”** Use text, not color alone; candidate edits must not dismiss this message while disposition remains Review.
- Show `Assessment_Reasons__c` immediately below the disposition on the record page. A fixture with an unknown hard criterion must expose that specific unknown in the supplied summary, for example “Required salary information is missing.” Do not claim that every Review record has an unknown hard criterion: Review also covers other unresolved assessment cases.
- The current projection cannot reliably filter individual unknown hard criteria. Do not parse free-text reasons into a truth flag, infer eligibility from a null score, or use `Availability__c=Unknown` as an eligibility proxy. If upstream summaries omit the actionable unknown, record an assessment/SYNC-01 projection dependency; do not fabricate a reason or claim the unknown-detail acceptance passed.
- Include blank disposition in the review queue as a distinct **“Assessment missing — eligibility not established”** case, with separate blank-disposition report grouping and record guidance. Preserve the underlying null; never convert it to Eligible, Review, or Rejected during a UI save.
- `Unknown`, `Not Seen`, and blank availability remain distinguishable from `Unavailable`. No availability value changes candidate progress. An Eligible record with unknown availability remains machine-eligible but visibly has unconfirmed availability.
- A blank score means no score supplied, not zero or rejection. Display score with its scale when present; describe it as a ranking signal, not an offer probability. Do not infer the assessment method or invent model provenance from score presence.

### Views and precise inclusion rules

Filters below are logical predicates, to be compiled into supported list/report metadata and verified against fixture record IDs. Let `D` = machine disposition, `P` = candidate progress, `A` = availability, `F` = follow-up date, and `T` = the candidate's current Europe/Berlin date. For reports and views use all records accessible to the candidate, **not “My records”**: the worker may own ingested jobs. Record/report access remains subject to SF-02 and org sharing.

All views include title, Company, Application Progress, Assessment Disposition, Availability and Follow-Up Date. Add the columns below where supported. Notes/reasons/source URLs are available on the record page; do not depend on Long Text Area list filtering, grouping, or inline editing. List views may overlap deliberately.

| Member suffix after `JA_` | Candidate label | Exact inclusion | Additional columns and intended order |
|---|---|---|---|
| `Eligible_Jobs` | Eligible Jobs — Machine Assessment | `D = Eligible` | Score, scale, last evaluated; last evaluated descending. Includes unavailable/archived records with those states visible; optional personal narrowing must not change this baseline definition. |
| `Review_Jobs` | Review Jobs — Unknown Eligibility / Assessment | `D = Review OR D is blank` | Last evaluated; oldest evaluation first with missing timestamps visibly identifiable. Includes records already shortlisted/applied; candidate action does not resolve machine review. |
| `Shortlist` | Your Shortlist | `P = Shortlisted` | Candidate Decision; title ascending. No eligibility or availability filter. |
| `Applications` | Your Active Applications | `P IN (Applied, Interviewing, Offer)` | Interview Date, Candidate Decision; follow-up ascending, blanks not presented as due. No eligibility or availability filter. |
| `Follow_Ups_Due` | Follow-ups — Due and Overdue | `F is not blank AND F <= T` | Candidate Decision; earliest follow-up first. Includes terminal progress states so an explicitly retained date is never silently lost. |
| `Follow_Ups_Upcoming` | Follow-ups — Upcoming | `F is not blank AND F > T` | Candidate Decision; earliest follow-up first. No implicit horizon or eligibility filter. |
| `Tracked_History` | All Tracked Jobs / Application History | No additional state/date filter | Candidate Decision, Interview Date, last evaluated; title ascending. Includes blank progress, Rejected, Withdrawn and Archived. This is current-record history access, not a complete event ledger. |

Use supported relative-date operators for due/upcoming, and test their actual date boundaries. Do not bake 1 November 2026 into deployed filters. If the platform cannot serialize the intended order, record the supported default and verify candidate sorting; membership predicates remain mandatory. Do not add broad record-type exclusions that hide legacy rows.

### Reports

Use one row per accessible Job. Default report date range is all time unless the predicate explicitly uses Follow-Up Date; do not silently constrain Created Date. Reports link to the Job for editing. Counts describe **Salesforce-tracked jobs**, not all locally discovered or rejected jobs. Never initially publish local-only rejects to fill a report.

| Report member under `Job_Tracker/` | Filters and grouping | Required interpretation |
|---|---|---|
| `JA_Eligible_Review` | `D=Eligible OR D=Review OR D is blank`; group by D, then A | Eligible, Review and missing assessment remain separate groups; no pooled “qualified” count. Display P, evaluation time and optional score/scale. |
| `JA_Shortlist` | `P=Shortlisted`; group by D, then A | Candidate shortlist may contain review, rejected or unavailable jobs. Include candidate decision and follow-up date. |
| `JA_Applications` | No progress filter; group by P, then D; show A | Current pipeline counts include New/Review/Shortlisted and terminal/blank groups. It is not a conversion-rate, submission-date, or event-history report; those inputs do not exist. |
| `JA_Follow_Ups` | `F is not blank`; group by F, ordered ascending | Candidate can narrow to `F<=T` or `F>T`; saved due/upcoming views provide daily action queues. Include P/D/A and decision; do not label retained terminal-state dates invalid. |

Use counts and dates; do not average incompatible score scales or replace null scores with zero. Report folders must be available to the intended candidate without exposing notes broadly. Share only within the approved access design; do not use public folder visibility as a substitute for permissions.

### Layout and editing specification

| Section/surface | Fields and behavior |
|---|---|
| Header/compact summary | Mapped title, candidate application progress, machine disposition and posting availability. Keep these visible together on the supported desktop viewport. Show Review/missing-assessment guidance above the detailed assessment. |
| Your application — editable | `Application_Progress__c`, `Candidate_Decision__c`, `Candidate_Notes__c`, `Follow_Up_Date__c`, `Interview_Date__c`. Permit saving edits and deliberately clearing optional values, including legacy blank progress. Standard Edit is the required complete path; inline editing is optional convenience. |
| Decision guidance | Visible wording: “Your decision changes your tracking workflow only. Source information and machine assessment stay separate.” Longer rationale belongs in Notes; do not silently truncate the 255-character decision field. |
| Machine assessment — read-only | Disposition, full supplied reasons, score with scale, last evaluated. No candidate edit control for these fields. Missing reasons/timestamp remain visibly missing, with no invented assessment. |
| Posting availability/source — read-only | Availability, Company, mapped title, source URLs. Preserve multiple source URLs and readable wrapping; these are source links, not guaranteed active application endpoints. |
| Technical reference — read-only/collapsed | Canonical ID, sync version/marker, and standard record identity as appropriate. Keep these out of routine candidate editing. |
| Company overview | Employer identity read-only and Jobs related list with title, candidate progress, disposition and availability; open the Job for candidate edits. |

Configure the candidate's display timezone as Europe/Berlin through the agreed setup process. Follow-up/interview dates retain date-only precision with no UTC conversion. Display evaluation DateTime using the candidate timezone while preserving the underlying instant. A follow-up date is a personal action date, not a deadline scraped from a posting.

Use page layouts for presentation and field permissions for effective access across records, lists, reports and other interfaces; a read-only layout alone does not establish field-level protection. See Salesforce's [field access rules](https://help.salesforce.com/s/articleView?id=platform.customize_fieldaccess.htm&language=en_US&type=5). SF-02 must inspect effective access, including existing broad/admin grants; this plan does not claim an administrator can be restricted by adding a read-only permission set.

Access contract for SF-02: candidate can read Job/Company machine projections and edit the five candidate fields on accessible Jobs; worker can create/update machine fields and read candidate fields for backup, with no candidate-field writes or Delete grant from this integration. Candidate creation/cloning/deletion is not a required tracking action. Resolve identity/license constraints with existing org capacity; do not require a paid user. If candidate and worker use the same broadly privileged identity, record the limitation and test UI plus payload protection honestly rather than claiming separate effective FLS.

## Representative candidate journeys

| Journey | Actions | Observable outcome |
|---|---|---|
| Discover and shortlist | Open Eligible; inspect reasons/source/availability; set P=Shortlisted and add notes | Enters Shortlist. D/A/source facts are unchanged; decision is candidate-owned. |
| Review unknown eligibility | Open Review with missing salary/eligibility information; inspect the unknown reason; decide to ask the recruiter and set a follow-up | Remains visibly machine Review and appears in follow-ups. No “override to Eligible” action or inferred source fact. |
| Act despite uncertainty | From that review job, set P=Applied and record rationale | Visible in both Review and Active Applications. Machine reasons and unknown remain visible. |
| Tracked job becomes rejected/closed | Candidate has P=Interviewing with notes/dates; later ingestion sends D=Rejected and A=Unavailable | Leaves Eligible if previously eligible, stays in Active Applications and any due follow-up; notes/decision/dates preserved. No forced archive or application deletion. |
| Follow up today | Open Due and Overdue; contact employer outside this system; update notes and set tomorrow's follow-up | Moves to Upcoming; clearing the date removes it from both follow-up lists without changing progress. |
| Separate two kinds of Unknown | Compare Eligible/Unknown availability with Review/Active and blank disposition/Active | First is machine-eligible with availability unknown; second needs machine review; third has missing assessment. None is silently treated as confirmed eligible and active. |
| Revisit a finished application | Set P=Withdrawn or Archived; retain a follow-up intentionally; open All Tracked Jobs and Applications report | Record/history access remains and the retained date is still actionable; machine refresh continues independently. |
