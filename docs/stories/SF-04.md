# SF-04 — Org capacity and metadata portability

Status: **PLANNED — stories only; no implementation or live org verification performed**  
Phase: **0**, with explicit Phase 1 extension contracts  
Requirements: **R09, R16**; supporting **R04, R08, R14, R15**  
Planning date: **1 November 2026**  
Baseline: [IMPLEMENTATION_BLUEPRINT.md](../../IMPLEMENTATION_BLUEPRINT.md), especially §§4–6 and 8–10.

## Objective and scope

Measure the selected org's actual capacity and usage, keep Salesforce tracking data compact, retrieve and version only project-owned metadata, and supply verified candidate-data exports that OPS-01 can include in recoverable backups. Preserve canonical identities, company/job relationships, candidate edits, and captured application history across local recovery and a separately authorized replacement-org recovery.

This plan changes only this story document. Implementation must not change retention settings, delete org records/files/history, prune local data, provision another org, deploy metadata, or automatically import candidate data. Metadata retrieval and data export are read-only remote operations. Existing retention expectations remain in force: protect identities, referenced revisions, application history and unfinished work; OPS-01 owns retention and backup destinations. No automatic expiry or remote archive/purge policy is introduced here.

**Metadata portability and data backup are separate deliverables.** XML source and manifests recreate configuration, not application records, candidate notes, historical values, attachments, or credentials. Candidate exports preserve observed data, not a deployable schema or a transactionally consistent copy of the whole org. OPS-01 combines compatible metadata references, local database/files and remote export evidence; each has its own coverage and verification status.

## Shared contracts to settle first

Names in this section are proposed SF-04 contracts. Reuse existing records where compatible; do not silently enlarge C07/C12 meanings or label a changed serialized contract as the old version.

### Capacity observation and decision

Each observation binds to source org ID, configured API version, UTC measurement time, evidence source, and mapping/config version. Each resource has a name, unit, observed maximum, remaining, computed used, freshness/status and reason. Read `DailyApiRequests`, `DataStorageMB`, `FileStorageMB` from the actual limits response when returned. Preserve additional relevant resource keys without treating absent values as unlimited. `used = maximum - remaining` only for valid comparable values; null, malformed, negative or inconsistent observations are unknown, not zero. Zero maximum is explicitly unavailable/unknown as appropriate, never a division by zero.

Keep the limits response's MB units explicit; any byte conversion for forecasts must document its convention and uncertainty. Supplement aggregate storage with authorized Setup Storage Usage evidence and scoped record/file inventory when available. Distinguish measured org totals, project counts/bytes and estimated incremental growth. Other applications consume the same org allowances. The REST resource reports allocations and remaining amounts, and measurements can lag consumption; do not promise an exact real-time reservation. See [Salesforce REST Limits](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-limits.html).

Produce separate `ok|warning|blocked|unknown` decisions for record publication, Files uploads, and export/metadata reads, with configured reserves, planned cost, reason, recheck policy and evidence age. An observation is not a guarantee that a subsequent write succeeds. Requests, retries, reconciliation, pagination and retrieval consume budgets too. Preserve SFCLIENT-01 per-operation budgets; an org-wide allocation is a different limit.

### Portable data export

Use versioned UTF-8 JSON/JSONL as the authoritative format so absent values, nulls, Unicode and date precision survive. CSV may be an explicitly secondary operator view, never the sole recovery representation. Put sensitive exports under a configured absolute local runtime directory outside source control. Do not emit row bodies, notes, tokens or raw payloads in console diagnostics.

| Package part | Required contents / semantics |
|---|---|
| Export manifest | Schema/format version, immutable export UUID and scan ID, source org ID/API version, mapping version and hash, metadata revision/digest, start/end UTC times, capture method/scope, principal/access evidence, filters, per-object expected/read/saved/skipped/error counts, missing fields, pagination completion, consistency/coverage status, omissions, local backup linkage, file paths/lengths/SHA-256 hashes. Secrets are excluded. |
| Companies | Canonical company UUID, source org + object + Salesforce ID, mapped name/required reconstruction values, modification token and observed time. Include every referenced project parent and any other Company rows expressly in the declared scope. |
| Jobs | Canonical job UUID, source org + object + Salesforce ID, canonical company UUID plus original Company lookup ID, mapped title and required reconstruction projection, all five candidate fields, source modification token and observation time. Preserve optional null Company lookups. Include tracked rejected, unavailable, archived and blank-progress jobs; do not reuse eligibility/list-view filters. |
| Candidate snapshots | Existing snapshot UUID, canonical job UUID, source org/record ID, mapping version, observed time, original source token, payload hash and exact field-presence map. Preserve historical local snapshots as well as the selected latest complete snapshot. An old snapshot cannot silently satisfy a new scan. |
| Available field-history archive | When enabled/queryable, source org + history object + history record ID, canonical parent key, source parent ID, field, event time, actor reference, and typed old/new values or explicit unavailable-value reason. Preserve source references locally; do not promise these rows can be reinserted as native Salesforce history. Record access/range/field coverage and gaps. |
| Linkage to local recovery | Bind C07 canonical IDs and local posting revisions/merge lineage via the OPS-01 backup ID and local cut time. Preserve remote mappings and C12 reconciliation identities in local backup; do not derive canonical IDs from mutable names, titles, URLs or hashes. |

Null means explicitly cleared/unknown as returned, not missing permission. An omitted required candidate field makes coverage incomplete; never coerce omission to null or an empty string. Date fields stay `YYYY-MM-DD`; machine events use UTC with offsets. No shortening, newline normalization that changes values, or loss of German characters in candidate data.

Scope completeness is measured against the declared project record universe and effective access, not `COUNT(canonical_jobs)` or only locally known remote IDs. Export visible in-scope remote rows even if local mappings are absent; unresolved/missing/duplicate canonical IDs and inaccessible parents go into a local issue file and block complete portable coverage. Never assign new canonical identities during export. Reconcile local tracked mappings with remote enumeration and report missing rows; absence alone is not authorization to delete or recreate anything. A zero-row export is complete only with positive scope/access/scan evidence.

Remote reads span an interval. Persist per-row `SystemModstamp` (explicitly selected), real scan start/end and the relationship to the local backup cut. Check changed rows/parent links at the end using a bounded stabilization pass; repeated changes, deletion, permission changes or unresolved count differences produce partial/unstable coverage. Do not claim an atomic org snapshot or a single global Salesforce/SQLite transaction. A local maintenance lock cannot stop candidate edits in Salesforce.

Application history here means recoverable captured candidate snapshots and available source history, including inactive applications. It does not promise every edit between scans, values predating capture, or inaccessible/expired history. Long-text field history does not preserve full prior values; therefore notes require full-value snapshots. Record actual coverage and recovery-point age rather than changing retention. See [Salesforce Field History Tracking](https://help.salesforce.com/s/articleView?id=tracking_field_history.htm&language=en_US).

### OPS-01 handoff and restore identity

- Supply the existing `RemoteRecoveryExport` summary with truthful object coverage, counts, real capture interval, per-record tokens and package checksum. Use existing completeness values (`complete`, `partial`, `incomplete`, `local_only_absent_sf04`) plus structured reasons/details through an explicit versioned extension where necessary. Missing SF-04 is different from present-but-failed or stale export.
- Coordinate `RemoteRecoveryPort.capture_remote_export(engine, config)` implementation/injection. The durable package includes rows, relationships and verified file hashes; a summary checksum alone is not a backup. OPS-01 must copy/package it, include files in `BackupManifest`, verify them independently and record omissions before publishing backup completion.
- `backup.remote_export_freshness_hours` and `backup.require_remote_export` already exist. Reuse and enforce them. Local-only backup remains possible under existing policy with `complete_local`/degraded reporting; a required remote export must fail visibly if absent, stale, partial or corrupt. Never promote partial coverage because a previous checkpoint was complete.
- Same-org recovery joins by canonical IDs within the source org, checks current IDs and candidate values/tokens, and retains newer remote edits. `SystemModstamp` can reflect machine changes too: a later token is a conservative conflict signal, not proof of a candidate edit. Missing/unparseable tokens, equal-token/different-value cases and identity mismatches require review; compare UTC instants, not arbitrary strings.
- Replacement-org recovery deploys reviewed compatible metadata separately, then restores Companies by canonical company ID, Jobs by canonical job ID with remapped Company lookups, and candidate values through a separately authorized recovery path. Preserve canonical UUIDs; build target-specific remote mappings. Original Salesforce IDs are provenance only, not valid foreign keys in the new org. Autonumber fields are not written as titles. Resolve owner/user references explicitly rather than copying source User IDs.
- OPS-01's restore remains local and inert. Candidate recovery must never enter the normal machine-field outbox or widen worker FLS. Emit a reviewable recovery package/conflict diff; remote import execution is outside these stories. Keep history archives locally readable and linked even where native history replay is unsupported.
- Phase 1 extension: preserve stable request identity (source org + record ID for UI-created C13 requests, or explicit client key), canonical job relationship, local request/artifact/version IDs, ContentDocument/ContentVersion/ContentDocumentLink mappings, hashes, review state and supersession links. Request metadata is metadata; request records, file binaries and reviews are data. Record unsupported coverage until SF-05–08/GEN-06 handoffs exist. Local artifacts alone cannot prove that candidate-edited remote Files were backed up.

## SF-04-S01 — Establish measured capacity and consumer decisions

**Objective:** replace quota assumptions with authenticated, dated observations and operation-specific decisions.  
**Dependencies:** SF-00/01, SF-02, SFCLIENT-01; OPS-01 adapter boundary.  
**Inputs → outputs:** target/mapping/settings + typed limits/usage evidence → versioned capacity observations, forecasts and decisions.  
**Owned files:** proposed capacity/settings/record modules, capacity schemas/fixtures, `SF-04/capacity.md`; minimal OPS capacity adapter wiring.

Tasks:

1. Validate expected org ID and API version against the authenticated session. Read real limits with `LimitsRequest`; map `raw_limits` storage categories and daily API fields correctly. Classify permission, authentication, unsupported resource, timeout and quota failures separately.
2. Collect dated total usage and scoped project record/file counts through available read-only interfaces; document unavailable Setup evidence explicitly. Include actual limits for relevant metadata/object/field allowances when discoverable; never substitute an edition table when not returned.
3. Fix the OPS adapter signature/field mismatch and remaining-versus-used error with an owner-coordinated patch. Preserve unknown values and resource-specific timestamps. Integrate remote decision status without incorrectly blocking local read-only capacity inspection for a remote outage.
4. Estimate queued new records, updates, future files and read-call cost, with provenance and margins. Do not promise that shorter fields reduce storage billing or multiply a presumed bytes-per-record constant into an authoritative capacity figure.
5. Validate configurable warning/block thresholds, absolute/percentage reserves, freshness and bounded recheck budget. Record these as application policy, separate from org quota. No hardcoded universal MB, daily-call or record-count cap.

Acceptance and verification:

- Two synthetic orgs with different Max/Remaining values produce different headroom decisions. A synthetic maximum of 100 and remaining 25 reports used 75; this fixture is not an org quota.
- Missing FileStorage, zero maximum, malformed values, stale evidence and permission denial never become healthy/unlimited. Configured API version is used instead of embedding `v60.0` in requests.
- Real gateway-shaped fixtures exercise the OPS adapter. Local capacity output still works during remote outage and reports unknown/degraded remote status. Exhausted remote API does not trigger an unbounded limits-poll loop.
- Live acceptance records actual org-bound measurements and evidence time or remains explicitly pending. No org records are created to fill storage for a test.

Configuration/migration impact: add versioned non-secret SF-04 policy configuration; no retention setting or remote schema change. Any additions to OPS records include backward-compatible deserialization and regenerated schemas.

**Dependencies:** S01, SF-01 mappings, SYNC-01; OPS-01 and GEN-06 consumer agreements.  
**Inputs → outputs:** current XML/Describe and C07/C11/C12 projections → data-placement rules, payload checks and failure contract.  
**Owned files:** `SF-04/compact-data.md`, portability validation/tests; coordinated boundary checks in SYNC-01, without redesigning its mapper.

Tasks:

1. Document Salesforce's compact projection: canonical IDs, names/title, Company lookup, availability/disposition, concise reasons, score/scale, evaluation time, source URLs, reconciliation markers and candidate state. Local SQLite/files retain raw source payloads/HTML, full normalized descriptions and revisions, provenance, profile evidence, prompts/results, detailed logs and full artifact history.
2. Respect actual mapped field lengths and types. Reasons are a versioned machine summary, not raw JSON/logs; URLs remain usable whole URLs. Preserve the full source locally. If required content cannot fit, return a visible validation/capacity issue; do not silently truncate candidate fields, identities, titles or URLs. Any future summary shortening requires an explicit deterministic convention and visible omission indication agreed with SF-03/SYNC-01.
3. Keep initial publication eligible/review only, but retain machine refreshes for already-tracked rejected/unavailable jobs. Capacity never changes eligibility, archives an application or resets progress.
4. Implement/test the consumer decision contract below with fakes; actual outbox/upload state transitions stay owned by SYNC-01/GEN-06. Preserve local artifacts, IDs, retries and reconciliation evidence.

| Condition | Required behavior |
|---|---|
| Warning threshold reached | Report resource, actual measurement/time, projected cost and configured reserve. Continue only operations that pass their checks; do not delete, buy storage or change retention. |
| Insufficient/unknown stale data headroom | Defer new capacity-consuming publication by default. Updates require their own validated budget; do not presume updates cannot consume storage. Preserve queued operations and local assessment, and expose reason/recheck state through existing retry/error contracts. |
| File capacity insufficient or upload rejected | Keep local artifact and `upload_pending`; preserve upload reconciliation marker, do not announce Ready, and do not discard prior remote versions. GEN-06 owns resumption. |
| API allowance/reserve exhausted | Stop discretionary reads/writes, preserve scan checkpoints and outbox, use bounded retry/recheck timing and server guidance. Do not assume reset at local midnight or that the next retry will succeed. |
| Permission/configuration failure | Actionable blocked/unknown result; no blind retries or automatic permission grants. |
| Local export/staging disk insufficient, interrupted write or checksum failure | Keep previous verified export, mark new attempt failed/partial, leave resumable evidence and publish no complete marker. OPS-01 determines whether local-only backup is allowed. |
| Server reports capacity error after a healthy preflight | Treat server response as authoritative; preserve pending work and refresh evidence within budget. Ambiguous writes still require existing reconciliation before resend. |

Acceptance and verification: raw-payload/log sentinel fixtures never appear in Salesforce projection; candidate content remains exact; oversized fields fail visibly; rejection/closure retains candidate data; each failure row has a bounded, restart-safe test. No deletion endpoint, retention edit, or new automatic scheduling is involved.

Configuration/migration impact: document projection version and optional machine-summary budget; distinguish character limits from org storage allowances. Keep existing retention and all candidate-field metadata unchanged.
