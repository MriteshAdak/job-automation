## Scope and dependencies

SF-05 owns the durable request object, relationships, fields, defaults, validation rules, scoped access, minimal offline-worker inspection surface, metadata compatibility checks, packaging and migration/handoff instructions. It defines the contract for consuming those fields; it does not take over generation orchestration.

| Dependency or consumer | Required agreement |
|---|---|
| **SF-01, FND-01 — direct prerequisites** | Resolved Job API name/canonical ID mapping; C13 schema, enums, errors, UTC and UUID conventions. |
| **SF-00/SF-02 — deployment/access gates** | Existing-org name ownership, capacity, supported metadata/API behavior, effective user permissions and a confirmed target binding. Reuse existing org/entitlements; no paid user seat or replacement org prerequisite. |
| **GEN-01/GEN-02 — integration consumers** | Mapping extensions, stable identity, immutable admission options, durable freeze before Running, timestamp/error/result projection, recovery and readback. GEN-02 owns the unavailable-job check and exact frozen inputs. |
| **SFCLIENT-01 — gateway consumer** | Typed record reads/updates, Describe/FLS checks, bounded errors and correct org binding. No new OAuth flow in SF-05. |
| **SF-06 — downstream** | Creation actions/Flows, active-identical-request reuse, queued feedback and explicit override/regeneration. SF-05 provides defaults and immutable request contracts, not those actions. |
| **SF-07/GEN-06/SF-08 — downstream** | Versioned Files links, accessible delivery, per-version human approval and notifications. SF-05 provides inspectable states/references, not upload/review/notification implementation. |
| **SF-04/OPS-01 — portability consumers** | Explicit metadata members, request identity/relationship export requirements and protection of unfinished work. Existing Phase 0 export coverage must not be described as including Phase 1 requests/Files. |

No drafting, inference, rendering, polling-loop redesign, automatic retry scheduler, generation action Flow, file approval workflow, notification automation, application submission or Phase 2 automation is included. Minimal mapping/validator wiring needed to express SF-05 compatibility is allowed; missing consumer behavior is an explicit integration gate, not an invitation to implement another component wholesale.

## Contract and design decisions

The following physical types, lengths, labels, access decomposition and inspection layout are **proposed engineering choices**, not separately confirmed user preferences. Exact supported metadata syntax is verified against the configured platform during implementation. Existing wire values and C13 meanings are compatibility requirements.

### C13 field mapping

Proposed object: `Generation_Request__c`, label “Generation Request”, plural “Generation Requests”; searchable/reportable, with an Auto Number `Name` such as `GR-{000000}` for display only. Use private internal/external sharing with an explicit, narrow worker row-access arrangement. Neither the display number nor a content/options hash is an identity key.

`I` means supplied at insertion and immutable thereafter; `W` means worker-managed; `S` means Salesforce-managed. Ordinary candidates can read all compact request fields but cannot edit worker fields.

| Logical C13 value | Proposed physical representation | Ownership, defaults and constraints |
|---|---|---|
| `salesforce_request_id` | Standard `Id` | S; stable UI request identity, canonicalized to 18 characters for local mapping. Never store a UUID in a Salesforce lookup. |
| `request_id` | Durable local UUID; no required custom remote UUID field | Derived/reconciled by GEN-01 as described below. A UI insert works while the local application is off. |
| `schema_version` | `Contract_Schema_Version__c`, Text(16) | Default `1.0`; immutable contract marker. Future unsupported versions fail compatibility checks rather than being silently coerced. |
| `client_request_key` | `Client_Request_Key__c`, Text(255), Unique, External ID, case-sensitive | I; optional/blank for UI creation, mandatory at the future external-creation boundary. Nonblank keys cannot be changed or cleared; a blank UI key cannot be populated later to rebind identity. No generated default. |
| `canonical_job_id` | Required `Job__c`, Lookup to resolved SF-01 Job | I; resolve parent `Canonical_Job_Id__c` to the local UUID. Use a restrict-delete lookup, not master-detail/cascade deletion. Proposed child relationship name `Generation_Requests`. |
| `document_type` | `Document_Type__c`, restricted Picklist | I; API values `cv`, `cover_letter`; explicit selection, no guessed document type. Labels “CV”, “Cover letter”. |
| `target_language` | `Language__c`, restricted Picklist | I; API values `de`, `en`, default `de` matching C13; a document option, never a candidate proficiency claim. |
| `template_id` | `Template_Id__c`, Text(255) | I; required nonblank stable template ID, no fabricated `default_template` catalog entry. Worker resolves an installed compatible template; SF-06 will offer valid choices. |
| `context_strategy` | `Context_Strategy__c`, restricted Picklist | I; `json`, `rag`, default `json` matching C13. Both are first-class choices. |
| `allow_unavailable_job` | `Allow_Unavailable_Job__c`, Checkbox | I; **default false**. Only explicit candidate intent at creation can set true. Worker cannot grant itself the override. |
| `state` | `Status__c`, restricted Picklist | W; default `Pending`; exact API values in the state table below. Read-only on candidate layouts/FLS. |
| `created_at` | Standard `CreatedDate` | S; original remote creation time for remote-origin requests, not polling/admission time. Preserve local-origin creation time separately when such creation is introduced. |
| `claimed_at` | `Worker_Claimed_At__c`, DateTime | W; initially null; first durable claim time, retained on resume. |
| `completed_at` | `Completed_At__c`, DateTime | W; initially null; terminal ready/failed time. Preflight failure may complete without ever being claimed. |
| `frozen_input_versions.posting_revision` | `Frozen_Posting_Revision__c`, Text(255) | W; nullable before claim, exact revision reference when frozen. |
| `frozen_input_versions.profile_version` | `Frozen_Profile_Version__c`, Text(255) | W; exact approved profile version; no profile evidence body. |
| `frozen_input_versions.policy_version` | `Frozen_Policy_Version__c`, Text(255) | W; exact policy version. |
| `frozen_input_versions.template_version` | `Frozen_Template_Version__c`, Text(255) | W; resolved version distinct from requested template ID. |
| `predecessor_request_id` | `Predecessor_Request__c`, nullable self Lookup | I; restrict deletion, proposed child relationship `Regenerations`; map remote predecessor ID to local UUID, reject self-reference. Deliberate regeneration gets a new record/key. |
| `result_artifact_ref` | **New** `Local_Artifact_Ref__c`, Text(255) | W; opaque C14/local result-set reference. No absolute Windows path, document body or localhost link. This explicitly maps the local C13 result meaning. |
| Existing remote result projection | Existing mapped name `Result_Artifact_Ref__c`, Text(255) | W; label “Delivered file reference”. Preserve current coordinator meaning: primary remote file ID. It is not the local C13 artifact reference or proof of approval; no silent repurposing. |
| `error.category` | `Error_Category__c`, restricted Picklist | W; nullable; exact C13 `ErrorCategory` values, verified against the current enum. |
| Error reason code | `Error_Reason__c`, Text(255) | W; preserve existing mapping; e.g. `job_unavailable`, not an unbounded traceback. |
| `error.message` | `Error_Message__c`, LongTextArea(2000) | W; concise sanitized explanation and actionable next step, not raw input/prompts/logs. |
| Detailed local error reference | `Error_Ref__c`, Text(255) | W; nullable opaque reference to durable local diagnostics; no credentials, raw candidate facts or arbitrary executable URL. |
| Projection reconciliation | `Operation_Marker__c`, Text(255) | W; existing GEN-01 operation token; separate from request/client identity and upload reconciliation markers. |
| Last remote change | Standard `LastModifiedDate` / `SystemModstamp` | S; inspection/change-detection metadata, not substitutes for claim/completion timestamps. |

C13 `ClassifiedError.recoverable`, details and field path remain in the local typed error. The remote category/reason/message/reference is a compact projection; do not claim full lossless reconstruction from those columns alone. The exact local C14 artifact/set reference and its format-to-remote-file/version mapping remain durable locally. SF-07/GEN-06 own additional version-specific Files references and approval records; a primary file ID alone does not identify an approved version or all required formats.

The field lengths are remote projection bounds, not new universal C13 limits. C13's version/reference strings currently have no matching maxima. Add explicit preflight length checks and fixtures: do not truncate IDs, keys, hashes, template identifiers or frozen versions. Unsupported oversized values produce an actionable compatibility error before dispatch. Safe error-summary shortening, if needed, must retain the full local error and mark that detail is available locally.

### Stable identity and idempotency

1. **UI creation:** Salesforce creates the record without a worker or client key. `(confirmed org ID, canonical 18-character request Id)` is the remote identity. GEN-01 already derives local UUIDv5 using namespace `d3b07384-d113-4b68-b3d4-b97c6d66e709` and the name `<canonical_org_id>:<canonical_request_id>`. Reuse this algorithm; do not substitute a random UUID on every poll or cast the record ID to a UUID. Equivalent 15/18-character representations map to the same identity without changing the original ID's case.
2. **Future external creation:** caller allocates a durable, namespaced key once, e.g. `producer:<uuid>`, and persists it before sending. Keys are unique within the target org's request object; local identity storage must also bind the org. Case is significant, leading/trailing whitespace and empty non-null keys are rejected at that boundary, and the exact normalized form is reused. UI null keys can coexist.
3. **Replay:** same client key and identical immutable job/options/predecessor intent returns the original request, including after completion or a lost response. Same key with different intent is a conflict, never an overwrite or a fresh generation. Unique External ID metadata prevents duplicate rows; an upsert alone does not prove payload equality. External creation logic and its effective create permissions are future work, not enabled by this story pack.
4. **Retry versus regeneration:** retry/resume retains Salesforce ID, local UUID, client key and frozen inputs. Deliberate regeneration uses a new Salesforce record/local UUID/client key when applicable, with a predecessor link. Neither identical options nor a shared Job lookup makes distinct deliberate requests duplicates. Active-identical-request reuse belongs to SF-06.
5. **Conflict and restore:** never bind an existing local request to a different org/remote ID merely because its client key matches. Restoring to a replacement org requires an explicit identity-remapping migration preserving original UUID/lineage; naïvely deriving new UUIDs would change identity. Do not invent a missing predecessor or job mapping.

### Processing, frozen versions and approval

| C13 state | Salesforce API value | Candidate-facing meaning / invariant |
|---|---|---|
| `pending` | `Pending` | Queued; may remain here indefinitely while the worker is offline. Newly created record has no fabricated claim, versions, completion or result. |
| `running` | `Running` | Durable local request and all four frozen versions already committed; claim time and the same versions projected together. An offline worker leaves the last observed state visible. |
| `upload_pending` | `Upload_Pending` | Output is awaiting accessible delivery; capacity/network errors may explain the delay. Do not advertise Ready or assume a local artifact is remotely accessible. |
| `ready_for_review` | `Ready_for_Review` | Required formats are delivered and accessible under GEN-06/SF-07 checks; completion/result references exist. **Ready for review does not mean approved.** |
| `failed` | `Failed` | Actionable failure is inspectable with completion time and concise error. Preflight `job_unavailable` can fail directly from Pending with no claim/frozen versions. |

`Unknown` is a local observation/quarantine condition, not a sixth processing picklist value. Human `draft`, `approved`, `superseded` status belongs to C14/SF-07 per specific artifact version. SF-05 adds no request-level `Approved` status/checkbox and grants the worker no approval authority. Job availability, assessment disposition and candidate application progress remain separate and unchanged.

Freeze rules: the four version fields start null, are populated atomically from durable GEN-02 output before/with Running, and cannot later change or clear. A nonempty frozen set must be complete. Claimed time cannot be reset on retry. Input options, Job/predecessor relationships, client key and schema marker are immutable from creation, closing the poll-versus-edit race even while Pending. A changed option or unavailable-job override requires a new request; setting the override never alters Job availability or eligibility.

Use validation rules for insert defaults, immutable inputs/key/frozen values, complete claim sets, timestamp consistency and terminal-field requirements. Enforce `claimed_at >= created_at`, `completed_at >= created_at` and, when present, completion no earlier than claim; surface clock skew rather than fabricating event times. Do not assume C13 currently enforces these stricter rules. Reopening retryable failed work, if supported by GEN-01, must explicitly clear terminal completion/error projection while retaining first claim/frozen versions; validate that recovery payload before enabling rules. Do not add a second retry state machine in Salesforce.

### Scoped permission contract

| Principal | Request CRUD and field access | Row/access limits |
|---|---|---|
| Candidate requester/inspector | Read/Create; no Edit/Delete by default. Writable at creation: Job, document/language/template/context options, explicit unavailable override and optional predecessor. Read-only state, claim/completion, frozen versions, result/error/marker/schema/client-key fields. | Own/project-authorized requests and readable parent Jobs only. Minimal tab/layout/list access; no approval grant in SF-05. |
| Existing `Job_Automation_Worker` | Add request Read/Edit, no Create/Delete. Read input/identity fields; edit only worker-owned status, timestamps, versions, result/error and operation-marker fields. | Must actually read/update candidate-created requests through explicitly verified sharing/ownership. No View All, Modify All, broad profile change, approval field access or ability to set candidate override. Existing Job candidate fields remain read-only. |
| Future external creator | Separate future capability: Read/Create plus client-key/input fields; no operational status or approval authority. | Not assigned or automatically enabled by SF-05. Must implement payload-equality replay and explicit candidate authorization for an override. |
| Unrelated user | No request grants from this component. | No candidate details leaked through object/search/list visibility. |

Proposed candidate set: `Job_Generation_Requester`. Keep request-specific worker additions in the existing worker set, preserving all unrelated entries. Required/system fields must use supported Salesforce permission metadata; do not emit unsupported FLS entries just to mirror this table. Validate effective CRUD/FLS after deployment.

Permission sets are additive, and layout read-only flags alone are not security. Evaluate the assigned profile, all sets/groups and sharing together. A shared administrator session cannot demonstrate that worker field restrictions are effective. If the existing no-cost identity arrangement cannot isolate worker writes, record that live least-privilege gate as unmet with SF-02; do not buy a seat or claim a restrictive set removes broader grants. Private request sharing needs a documented candidate-to-worker row route; FLS alone does not provide it. Prefer an existing authorized principal/group and narrow sharing; do not grant global object visibility to make polling succeed.
