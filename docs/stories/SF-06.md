## Boundary, dependencies and ownership

SF-06 owns the two candidate actions, option selection, an atomic Salesforce enqueue/reuse boundary, deliberate-regeneration confirmation, unavailable-job consent, and immediate feedback linking the durable request. The synchronous portion performs only bounded Salesforce validation/read/write work. **Neither Flow, Apex nor browser code may call the Windows localhost model service, start inference, wait for a local worker, or require a local health check.** The manually started GEN-01 worker polls Salesforce outbound later.

| Dependency / consumer | Required contract or gate |
|---|---|
| **SF-05 — direct prerequisite** | Final request API names, defaults, immutable fields, five state values, predecessor relationship, inspection route, requester permissions and candidate-to-worker sharing; missing handoff is an explicit activation blocker. |
| **FND-01 / SF-01** | C13 `1.0`, enum/UUID/UTC conventions; readable Job with valid canonical UUID; separate remote and canonical identities. |
| **SF-00 / SF-02** | Confirm existing org, collisions/capacity, API support and effective access. No replacement org, paid seat, broad profile grants or new OAuth flow. |
| **SF-03** | Integrate actions into the existing Job layout/page without replacing tracking content or changing candidate decisions. |
| **GEN-01 / GEN-02** | Consume an immutable Pending request, preserve identity on polling/recovery, recheck availability and freeze current approved inputs at claim. SF-06 does not choose or fabricate frozen versions. |
| **GEN-02 / GEN-03 / GEN-05** | Agree valid request template IDs, document/language compatibility and their content/layout resolution. Publish a compact versioned choices snapshot for Salesforce; no runtime Windows lookup. |
| **SF-07 / GEN-06 / SF-08 — downstream** | SF-07 may call the same regeneration entry contract from request/file review. Delivery, version approval and eventual ready/failure notifications stay with these components. Immediate queued feedback is SF-06. |
| **SF-04 / OPS-01** | Extend exact metadata inventory and backup/restore coverage for SF-06 configuration and durable submission receipts; preserve request/receipt identity mappings. |

Out of scope: generating/rendering/uploading documents, implementing worker retry/recovery, file approval, readiness notifications, model installation, Phase 2 scheduling/automatic drafting and application submission. No existing request is reset to Pending by an action; no Job status, notes, decisions, follow-up, interview, assessment or availability field is written.

## Contracts and proposed implementation choices

The architecture, API names and UI wording below are **proposed engineering choices**, not separately confirmed user preferences. S01 resolves them against SF-05 and actual org metadata. A minimal invocable Apex service is proposed because a Flow “Get Records, then Create Records” sequence and disabling a button do not by themselves enforce concurrency safety.

### Actions and user options

Provide Job-specific **Generate CV** and **Generate Cover Letter** quick actions. Each starts a screen Flow with input `recordId`, fixes its document type, and delegates final submission to the same service. Opening or cancelling a screen creates no request. Cover-letter generation is optional and independent; neither action implicitly queues the other document.

| Input | UI and server contract | Request mapping from SF-05 plan |
|---|---|---|
| Job | Derived from the current record; reread and authorize server-side. Reject missing/wrong-object/deleted/inaccessible records or missing canonical UUID. | `Job__c` Salesforce lookup; canonical UUID resolved by GEN-01. |
| Document type | Fixed by action: `cv` or `cover_letter`; never trust an arbitrary browser-supplied type. | `Document_Type__c` |
| Language | German (`de`) / English (`en`); visible `de` default. Document language does not assert candidate proficiency or promise translation capabilities beyond GEN-03. | `Language__c` |
| Template | Required stable ID selected from enabled, compatible choices. Show readable labels; reject unknown/disabled/incompatible/oversized IDs. No free-text path, prompt or placeholder default. | `Template_Id__c` |
| Context | Both `json` and `rag`, with short explanatory labels; visible `json` default. No silent strategy substitution. | `Context_Strategy__c` |
| Unavailable override | Checkbox, false by default on every fresh intent: “Generate a draft even if this job is unavailable.” Never inherit true from a predecessor or stored user preference. | `Allow_Unavailable_Job__c` |
| Creation mode | Default `reuse_or_create`; separate explicit “Generate another draft” confirmation selects `regenerate`. This is a UI command, not a new C13 processing state. | No new C13 field required. |
| Predecessor | Required for regeneration; read-access check, same Job and document type, no self-link. Language/template/context may deliberately change. | `Predecessor_Request__c` lookup; GEN-01 resolves its local UUID. |
| Submission token | Opaque per-confirmed-intent identifier retained across resubmission; not editable, not an options hash or worker operation marker. | Separate SF-06 receipt; `Client_Request_Key__c` remains null for these UI requests. |

Server inserts only the permitted Job/options/predecessor fields. SF-05 supplies Pending, schema `1.0` and standard CreatedDate defaults. Claim/completion/frozen versions/results/errors remain empty. A new request receives a new Salesforce ID; GEN-01 derives its local UUID using the existing mapping algorithm. SF-06 never writes a local UUID into a lookup or changes the SF-05 client-key semantics.

Choices are a Salesforce-resident, versioned configuration snapshot maintained at release time. Each entry contains request template ID, label, document type, allowed languages, enabled flag and catalog version; a default must point to a real compatible entry. GEN owners provide the authoritative mapping to their local catalogs. Revalidate choices on submission; a catalog change during the dialog produces an actionable refresh error. The worker remains responsible for detecting local configuration drift at claim. No prompt, profile facts, model endpoint or Windows path belongs in the choices metadata.

### Active reuse, terminal requests and regeneration

Define **active** as exact Salesforce states `Pending`, `Running`, `Upload_Pending`. A stale Running request remains active: its age or a stopped worker does not authorize duplicate work. `Ready_for_Review` and `Failed` are terminal for this UI. Unsupported states/schema versions produce an inspectable compatibility issue rather than being treated as “no match.”

Define **identical** by the same authorized candidate scope, same canonical Job/remote Job binding, document type, language, exact template ID, context strategy and override Boolean. Use validated normalized wire values and a versioned comparison contract. For Phase 1, scope to the current candidate's requests (server-derived `CreatedById`); do not accept a candidate ID from the browser or reuse another user's work merely because its Job matches. Do not compare titles, display labels, description hashes, timestamps or current local profile versions. A hash may index this tuple but full equality must be checked.

| Situation | Required outcome |
|---|---|
| Ordinary submission, no matching request | Create one Pending request and return its ID after commit. |
| Ordinary submission, identical active request | Reuse it without changing options, timestamps, state or lineage. Return its actual observed state and link. This may be a previously deliberate regeneration with matching options. |
| Several identical active requests already exist | Return the oldest by CreatedDate, then Id, and flag the duplicate condition for inspection. Do not delete/merge any request or create another. Distinct deliberate requests keep their identities. |
| Only matching terminal history exists | Show existing outcome(s); do not silently queue again. Candidate selects a predecessor and explicitly confirms another draft. |
| Options differ | They are different intent. An ordinary request can be created if its own tuple has no match; changing an existing draft uses explicit regeneration and predecessor lineage. Never edit the original options. |
| Explicit regeneration | Create a fresh request even if an identical active request exists; show that existing work continues. Require fresh confirmation and a fresh submission token. Preserve predecessor, prior artifacts and approvals. |
| Same submitted intent is replayed | Return the receipt's original request even if it has since completed, failed, changed state, or another request now matches. Do not reapply current catalog validation to invalidate a committed replay; still enforce current access and exact original payload equality. |
| Same token, different payload/mode/predecessor | Conflict; zero writes and no identity rebinding. |

Predecessor is lineage, not part of ordinary active matching. It **is** part of immutable submission payload equality. Thus separate confirmed regenerations receive separate IDs, while a repeated click within one regeneration confirmation receives the same ID. GEN-01 retry/resume preserves the existing request and frozen inputs; SF-06 supplies no generic “reset/retry” operation that creates work implicitly.

### Unavailable-job consent

Display Salesforce availability as its last recorded observation. `Unknown`/blank and `Not_Seen` do not mean confirmed unavailable; show appropriate uncertainty without fabricating closure. GEN-02 is authoritative at claim and can detect an intervening closure.

For a Job already marked `Unavailable`, require explicit checkbox consent before a new request. A request queued while the Job appeared active may later fail with `Error_Reason__c = job_unavailable`; retain that request and error. The failed-request route reads the persisted reason server-side and offers “Generate anyway” only through a fresh confirmation with an unchecked override control.

**A new request following a `job_unavailable` failure requires explicit candidate override true**, even if the displayed Job has subsequently changed or the candidate changes language/template/context. Inspect same-candidate, same-Job/document-type failure history on the ordinary action as well as validating an explicitly selected predecessor, so reopening the Job action cannot bypass the failed-request gate. If an override-bearing successor has already been created, later ordinary clicks may reuse that active request after confirming the same override option; they must not create another automatically. A committed replay simply returns the earlier request.

When ordinary submission discovers this failure history and would otherwise create work, return `confirmation_required` and route through regeneration with an explicitly selected failed predecessor; changing the options does not remove this requirement. Consent is scoped to one confirmed submission. Store the chosen true value immutably on the new request, record its predecessor and the submitting candidate through standard audit fields, and bind consent to the receipt payload. Never mutate the failed request's override, copy predecessor consent automatically, turn a truthy string into true, change Job availability/eligibility, or infer consent from Applied/Shortlisted status. Worker failure without override stays visible; background retries cannot grant consent.

### Atomic enqueue and replay contract

Proposed service input `SF06SubmitV1`: contract/catalog versions, Job ID, fixed action type, normalized options, mode, optional predecessor, submission token, and explicit regeneration/override acknowledgments. Derive org and principal on the server. Do not accept processing fields, arbitrary sObject field maps, callback URLs or local-service settings.

Output: `outcome` (`created`, `reused_active`, `replayed`, `confirmation_required`, `rejected`, `retryable_conflict`), accessible request ID/name when present, observed processing state, safe record link, and concise reason/message. Output outcomes are action responses, not request picklist additions. Validation/access/lock errors must not return “Queued.”

Proposed transaction:

1. Enforce entry permission, sharing and explicit CRUD/FLS checks. Check the caller-scoped receipt first; exact replay returns its saved result after access revalidation, and payload mismatch fails. Never use a token as authorization.
2. Validate a new intent, current choices and consent. Lock the existing Job row, then recheck receipt, availability, relevant history and active matches in that transaction. Lock/recheck a selected active request before returning it; use consistent parent-before-child ordering. If state changes while waiting, evaluate the new state rather than enqueueing from a stale screen result.
3. For ordinary mode, reuse a matching active request or require terminal-history confirmation before inserting. For regeneration, verify the selected predecessor/consent and insert a fresh Pending request. Insert the submission receipt mapping the exact intent to the chosen request in the **same transaction**, including when reusing an existing request.
4. Commit before rendering success. If request or receipt insertion fails, roll back the compound operation. Unique receipt-key races resolve by rereading in a fresh transaction with payload comparison; bounded lock contention returns a retryable response with the same token. Never fall back to an unlocked create or an unbounded synchronous retry loop.

The proposed **`JA_Generation_Submission__c`** receipt is private, compact SF-06 coordination metadata, not a second generation queue. Proposed fields: unique case-sensitive `Submission_Key__c` (server-scoped principal plus opaque token), `Payload_Version__c`, canonical `Intent_Payload__c` (bounded options/IDs/consent only), `Request__c` restrict-delete lookup, and `Outcome__c`; standard audit fields establish actor/time. Full payload comparison prevents hash-only collisions. Only the reviewed service writes receipts; candidates get no general receipt Create/Edit/Delete capability and the worker needs none. Any narrowly elevated receipt DML must follow successful request CRUD/FLS/sharing checks and must not elevate request creation or reading. Receipts contain no secrets, free-text job/profile bodies or document content.

Persist the token before sending, keep it through double-clicks, Back/resubmit, refresh and ambiguous responses, and rotate it only on a separately confirmed new intent. A small Flow screen LWC may retain the unresolved token/intent in browser session storage scoped to org/user/Job/action. Treat this storage as untrusted input. If recovery storage is unavailable or lost, show request history and require explicit reconciliation/confirmation; do not silently mint another regeneration token. Document this boundary rather than promising browser storage survives every browser reset. Server receipts survive UI restarts and remain the authority when the token is available.

The parent lock serializes SF-06 submissions even when no request exists yet; a query that locks only an empty request result is insufficient. Guarantee this atomic boundary for SF-06 action callers. SF-05 standard record creation and future external producers are separate entry points: inventory them and document their scope; do not claim a global uniqueness invariant over legitimate deliberate requests. Future producers must coordinate their own creation semantics before joining this path.

Platform references: Salesforce documents [record context for Flow quick actions](https://help.salesforce.com/s/articleView?id=flow_distribute_internal_action.htm&language=en_US&type=5), [FOR UPDATE locking](https://developer.salesforce.com/docs/platform/salesforce-soql-sosl/guide/sforce-api-calls-soql-select-for-update.html), and [CRUD/FLS enforcement for Apex controllers](https://developer.salesforce.com/docs/platform/aura-platform/guide/apex-crud-fls.html). These support the proposed primitives; locking/security behavior, transaction boundaries and API `60.0` syntax still need target-platform tests. Sharing declarations alone are not sufficient CRUD/FLS evidence.

### Immediate feedback

- New request: “CV request GR-… queued. It will be processed when the local worker runs. You can close this window.” Include “Open request,” selected options and a human-review reminder. Use the corresponding cover-letter label.
- Reuse: “An identical request already exists: GR-… — Running” (or Queued / Awaiting upload). Explain that no additional request was created.
- Replay: return the original link and current observed state; a now-failed/ready request must not be relabeled newly queued.
- Uncertain response: “We could not confirm whether the request was saved. Check this submission again.” Preserve token/options and reconcile through the service.
- Definite rejection: identify the invalid option, access/configuration issue or contention and a safe next step. No stack traces, credentials, raw prompt/profile content or local paths.

Feedback appears after Salesforce commit, without waiting for inference or polling for completion. Pending can persist indefinitely while the worker is off. No invented queue position, ETA, heartbeat, delivery or approval. Readiness/failure notification automation belongs to SF-08; existing SF-05 request detail supports progress inspection meanwhile.

## SF-06-S02 — Implement atomic submission and durable replay

**Objective:** create/reuse one request per ordinary intent under races and preserve each deliberate regeneration.  
**Dependencies:** S01, SF-05 schema/access; SF-02 security review.  
**Inputs → outputs:** validated submission → one committed request/receipt result or a classified non-success.  
**Owned metadata/code:** proposed `classes/JA_GenerationSubmit.cls`, its metadata/test class, focused helper classes if needed, and `objects/JA_Generation_Submission__c/` under `salesforce/force-app/main/default/`.

Tasks:

1. Implement server validation, principal scoping, permissions, parent/selected-request locking, active comparison and atomic receipt persistence. Revalidate security after any replay lookup.
2. Keep UI request client key null and use existing Salesforce-ID-to-local-UUID identity. Do not overload `Operation_Marker__c`, template IDs or an options hash.
3. Implement ordinary, explicit-regeneration, terminal-history and unavailable-consent branches. Reject forged predecessor/Job/type/Boolean/status input.
4. Implement bounded contention/unique-key recovery, transactional rollback, same-token conflict and lost-response reconciliation. Handle multiple invocable inputs with a documented bounded batch contract, consistent lock ordering and no per-item unbounded queries.
5. Keep all request access subject to effective CRUD/FLS/sharing. Allow any narrow internal receipt write only after these checks; prevent direct receipt tampering and unrelated metadata access.

Acceptance: two concurrent ordinary submissions with identical options return one request; replay returns that request after any state transition; one confirmed regeneration submitted twice yields one new ID, while two independently confirmed regenerations yield two. Failures cannot leave an orphan newly created request without its receipt. The service makes zero callouts and schedules no generation work inside Salesforce.

Configuration/deployment impact: additive Apex and compact private receipt schema; request schema/worker behavior remain SF-05/GEN-owned. Confirm object/storage capacity and receipt backup coverage before activation.
