# SF-00 — Existing Dev Org inventory and deployment planning

Status: **PLANNED** · Planning date: **31 October 2026** · Phase 0 · Scope: **SF-00 only**

Baseline: [IMPLEMENTATION_BLUEPRINT.md](../../IMPLEMENTATION_BLUEPRINT.md), especially §§1–2, 5–10. This document defines implementation stories for a future read-only inspection. Local repository/configuration inspection informed this plan; **no live org inspection, authentication attempt, deployment, or org modification was performed for this planning task**.

## Objective and boundaries

Identify the existing Developer Org's available access, relevant schema, project-owned assets, actual capacity, and viable authentication paths. Produce an evidence-backed inventory, naming-collision register, and narrowly scoped deployment proposal for downstream owners.

Direct requirements: **R08** (tracking and preservation of candidate decisions), **R14** (native Windows and existing infrastructure), **R16** (auditability, capacity, recovery). **R15** applies throughout as a credential and privacy constraint. SF-00 has **no prerequisite component**; an existing authorized connection or administrator-assisted evidence is an inspection dependency, not a requirement to implement SF-02 first.

Confirmed constraints: use the user's existing org; do not assume it is empty; do not require a replacement org, paid integration-user seat, or paid tooling. Inspect before deciding what can be reused. Never include credentials or unrelated private records in reports.

SF-00 owns inspection notes, sanitized evidence summaries, inventories, unresolved-access records, and the deployment proposal. It owns **no deployed metadata, record changes, permission grants, app registrations, migrations, credential provisioning, or runtime code changes**. SF-01 owns tracking schema; SF-02 owns authorization changes; SF-03 owns tracking UI; SF-04 owns capacity enforcement and metadata portability. Phase 1 assets may be noted as collision/dependency context; implementing SF-05–08 is excluded. SF-09 and other Phase 2 work remain deferred.

## Inspection rules and evidence contract

The following artifact organization and inspection sequence are proposed engineering defaults, not claims of user-approved schema or authentication choices.

- Select exactly one intended existing org before remote access. Use an explicit target, never a default alias merely because it exists. If the target cannot be identified from available context, resolve that ambiguity with the user before connecting. Pin the verified identity in private connection configuration; reports can use a stable redacted org reference.
- Use authorized Setup views, REST metadata/limits reads, and scoped Metadata/Tooling API reads. Authentication/session renewal through an already authorized connection can create platform login/audit events and rotate local tokens; it must not change business records, metadata, app policies, or permissions. If establishing access requires new grants, app setup, or reauthorization, record the dependency for SF-02 instead of performing it in SF-00.
- Do not deploy or validate a deployment, execute anonymous Apex, run Flows/actions, upload files, drain sync/outbox work, run generation workers, create test records, change licenses/users, or perform cleanup. Do not use the smoke script's `--allow-write` option. A read-only metadata retrieve may write local files only to a controlled location outside tracked source; it is not a deployment.
- Discover only names/types/namespaces needed to identify relevant objects and collisions. Then narrow field, permission, and automation inspection to candidate project assets. No broad data export, unrelated record queries, candidate notes, CV contents, Files bodies, or user lists. Metadata can itself contain sensitive defaults, formulas, URLs, and embedded values; review before retaining it. Skip credential-bearing settings and redact sensitive expressions to their structural effect.
- Never dump CLI auth files, environment values, org-display/auth URLs, authorization headers, token responses, client secrets, private keys, passwords, or session-bearing URLs. Keep credentials in their existing protected store. Reports describe credential-reference availability and protection, never contents. Do not copy CLI tokens into repository configuration.
- Bound calls, pages, retries, and metadata scope before executing. Keep an inspection call ledger and stop on exhaustion or uncertainty. No automatic fallback to another cached org, broader access, or unbounded scan.

Each inventory row must include: stable item key; redacted org reference; observation time in UTC; source/API version or Setup page; inspection identity role (not personal details); evidence reference; visibility scope/completeness; observed facts; interpretation; owner; and next action. Distinguish **observed**, **administrator-reported**, **proposed**, **unknown**, **blocked**, and **not applicable**. An absent item is confirmed absent only when authoritative visibility covered its scope. A permission-filtered listing or failed describe cannot prove absence. Conflicting sources remain unresolved until reconciled.

Expected implementation outputs are a sanitized [future component handoff](../components/SF-00.md) and supporting tables under a proposed `docs/components/SF-00/` directory:

| Output | Required contents |
|---|---|
| `access.md` | Target-selection evidence; edition/type; API version support; UI/API/metadata visibility; inspector versus proposed worker permissions; tool availability; gaps and evidence freshness. |
| `schema.md` | Relevant object/field inventory, semantic ownership, relationships, constraints, permissions, and mapping compatibility. |
| `metadata.md` | Relevant asset names/types/namespaces, ownership evidence, repository counterparts, dependency edges, managed/unmanaged status, drift, and retrieval completeness. |
| `capacity.md` | Timestamped API/data/file allocations, used/remaining values and units, relevant structural limits, reserved headroom assumptions, and gaps. |
| `authentication.md` | Existing app/connection capabilities, feasible no-new-cost identity/flow options, prerequisites, policy restrictions, Windows credential handling, and client compatibility. |
| `deployment-plan.md` | Name-collision decisions, logical-to-physical mapping proposal, exact proposed members/dependencies, exclusions, deployment gates, preservation and recovery requirements. |
| `evidence-and-gaps.md` | Sanitized evidence index, commands/endpoints or UI navigation used, bounded-call ledger, blocked checks, owner/action/recheck conditions, and verification status. |

The implementation may consolidate these into the handoff if small, retaining all required tables. Any private supporting material stays outside source control in an access-controlled Windows directory; publish only reviewed, sanitized summaries. Do not retain sensitive raw responses merely to make evidence reproducible. No changes to C01–C15, runtime schemas, mappings, or credential configuration are needed for SF-00.

## Ordered implementation stories

### SF-00-S01 — Establish the intended org and inspection access

**Objective:** identify the existing Dev Org and the access that can safely be used now. **Requirements:** R08/R14/R16; R15 constraint. **Dependencies:** none. **Owned output:** `access.md` and initial evidence/gap register.

**Inputs and evidence:** current instructions; the local baseline above; redacted CLI configuration metadata; authorized existing session; Setup Company Information and permission summaries; supported API version discovery and live identity response where permitted.

**Tasks**

1. Recheck repository configuration, metadata paths, and available native Windows tools without exposing auth data. Locate a known CLI executable if present; installation is not a prerequisite. Resolve the intended cached connection privately, without connecting to unrelated cached orgs.
2. Establish the selected org identity, org type/edition, instance/My Domain, and approved inspection identity. Retain exact connection bindings privately; record a redacted matching result. Do not infer Developer Edition solely from hostname or alias. Confirm supported API versions instead of assuming the example version is usable.
3. Build an access matrix for Setup viewing, API access, relevant object reads, field visibility, metadata listing/retrieval, limits visibility, and future deployment permission. Record actual effective access and its source. Identify administrator availability without presuming the current user is an administrator.
4. Separate inspection privileges from future runtime privileges. Describe potential create/update permissions from metadata/configuration only; do not prove them through writes. Record row-sharing and field-security limitations and whether a more privileged administrator supplied specific evidence.
5. If using the existing gateway, require a live check with nonempty matching org/user identifiers and the intended origin. Missing identity, mismatch, unsupported version, or insufficient permission fails the relevant gate even if a helper reports success.

**Acceptance examples**

- Given several cached aliases, only the resolved intended org is contacted; reports omit other identities and cache secrets.
- Given UI access but no API access, UI-observed facts are retained, API checks are blocked with an owner/action, and no new org/app/permission is created.
- Given a mismatched or absent live identity, schema inspection stops; cached configuration is not accepted as proof of a connection.

**Verification:** manually review target binding and access evidence; record live, administrator-reported, and local-only checks separately. Missing access follows the handling table below. **Configuration impact:** none; any future binding corrections are handed to SF-02/SFCLIENT-01.

### SF-00-S02 — Inventory relevant objects, fields, and ownership

**Objective:** determine whether existing schema can meet current tracking mappings without harming unrelated data. **Requirements:** R08/R16; R15 constraint. **Dependencies:** S01 access gate, or explicitly scoped administrator evidence. **Owned output:** `schema.md`.

**Inputs and evidence:** blueprint §5; current `SyncMappingConfig` and payload builders; REST global/individual describe; Object Manager; scoped Metadata/Tooling API definitions and effective permissions. Salesforce's [sObject Describe reference](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-sobject-describe.html) defines the metadata read endpoint; describe is evidence about schema, not record ownership.

**Minimum mapping checklist**

| Logical area | Current example API names to inspect; these are not approved org names |
|---|---|
| Company identity/name | `Company__c`, `Canonical_Company_Id__c`, `Name` |
| Job identity/title/parent | `Job__c`, `Canonical_Job_Id__c`, `Name`, Job's `Company__c` lookup |
| Machine assessment/availability | `Availability__c`, `Assessment_Disposition__c`, `Assessment_Reasons__c`, `Relevance_Score__c`, `Score_Scale__c`, `Last_Evaluated_At__c`, `Source_URLs__c` |
| Reconciliation on both objects | `Sync_Operation_Marker__c`, `Machine_Sync_Version__c` |
| Candidate-owned Job fields | `Application_Progress__c`, `Candidate_Notes__c`, `Candidate_Decision__c`, `Follow_Up_Date__c`, `Interview_Date__c` |

**Tasks**

1. Check exact default names, relevant alternative objects, namespaced/package variants, and existing project conventions. Use names/type metadata for discovery; no business record sampling is required. Record existence separately from visibility and ownership.
2. For each relevant object/field, capture API name/label, namespace, type, size/precision/scale, nullability, required/default/calculated/autonumber status, External ID and unique flags, case sensitivity where exposed, relationship target/cardinality, delete behavior, and effective read/create/update capabilities. Note required fields absent from the current payload and any constraints that would block later inserts or updates.
3. Check UUID text capacity and unique External ID semantics; distinguish `externalId`, `idLookup`, and `unique`. Check whether `Name` can accept names/titles or is autonumber. Confirm Job's relationship points to the intended Company object. Check nullable scores/scales for rules-only assessments and sufficient numeric precision for sync sequence values.
4. Record allowed/active/restricted picklist values, record-type applicability, defaults, validation rules, and dependent picklists. Compare existing mappings: disposition `Eligible/Review/Rejected`; availability `Active/Not Seen/Unavailable/Unknown`. Keep application progress and candidate overrides separate from machine eligibility/availability.
5. Identify existing defaults/automation that might reset candidate fields on update. Record metadata effects and dependencies without triggering them or reading private field values. Candidate-field read capability is a future backup need; inventory does not perform backups.
6. Reconcile full metadata facts with the narrower gateway projection. Preserve unknowns instead of inventing sizes or claiming that a field is unique because it is an External ID. Record data migration/duplicate checks needed later if an existing field would become unique; do not perform that migration or retrieve duplicate values here.

**Acceptance examples:** an existing unrelated `Job__c` is classified as a collision, not adopted; an invisible object stays unknown; a nonunique canonical field blocks a reuse recommendation; an autonumber `Name` produces an explicit alternative title/name mapping; marker/version requirements appear for both objects. Every checklist entry has evidence or a named gap.

**Verification:** review mapping coverage and compatibility against current code and metadata; synthetic examples can demonstrate classifications but cannot establish live schema. **Configuration/migration impact:** proposal only; SF-01 and SYNC-01 own any later schema/mapping changes.

### SF-00-S03 — Establish metadata ownership and dependency boundaries

**Objective:** distinguish assets this project can later manage from unrelated or shared org metadata. **Requirements:** R08/R16; R15 constraint. **Dependencies:** S01 and S02 candidate asset list. **Owned output:** `metadata.md` and dependency inventory.

**Inputs and evidence:** current repository contents; scoped metadata listing/retrieve; Object Manager and automation configuration; relevant installed-package/namespace information; prior project manifests or owner confirmation if available.

**Tasks**

1. Inventory candidate objects/fields plus their relevant permission sets, tabs, applications, layouts/FlexiPages, record types, list views/reports, validation/duplicate rules, Flows, Apex triggers/classes, global value sets, and relationships. Include only existing request/Files/notification assets that could collide or affect these candidates; do not design Phase 1 features.
2. Classify each asset as project-owned, shared dependency, unrelated/protected, managed-package controlled, or ownership unknown. A matching label/API name, creator, or modification date alone is insufficient ownership evidence. Record explicit owner confirmation, namespace/package provenance, or a reviewed repository/manifest match.
3. Record active automation/dependencies that could change data, send notifications, require additional fields, or constrain later schema changes. Missing dependency API coverage is a gap; a zero-result dependency query is not proof there are no dependencies.
4. Compare confirmed project assets against local sources. Record remote-only assets, source-only candidates, version/API differences, drift, and retrieval restrictions. Use an explicit member allowlist for any read-only retrieval; do not retrieve the whole org or overwrite a future project's source tree. Broad profiles and credential-bearing metadata are excluded.
5. Keep retrieved source private until reviewed for secrets/private defaults. Publish only relevant names, structural summaries, dependency edges, and safe fingerprints where useful. Remote-only metadata remains preserved, not automatically replaced by new defaults.

**Acceptance examples:** remote project assets remain in the baseline despite the absent local `salesforce/` directory; an unrelated Flow referencing a candidate object becomes a protected dependency; managed-package ownership prevents a replacement proposal; partial metadata access yields a partial inventory with specific missing types/members.

**Verification:** review ownership evidence and dependency completeness for every proposed reusable asset. **Migration/configuration impact:** none; scoped retrieval/versioning strategy is handed to SF-04, and future source/package creation remains downstream work.

### SF-00-S04 — Measure API, storage, and relevant org allowances

**Objective:** establish actual remaining capacity and a bounded basis for later operational choices. **Requirements:** R14/R16. **Dependencies:** S01; S02/S03 for project-specific implications. **Owned output:** `capacity.md`.

**Inputs and evidence:** `GET /services/data/<verified-version>/limits/`, safe API usage headers where available, Setup Company Information/Storage Usage, and relevant object/feature allocation pages. Record source and observation time for each number.

**Tasks**

1. Capture `DailyApiRequests` maximum/remaining and derived used values; capture `DataStorageMB` and `FileStorageMB` or equivalent Setup figures with explicit units. Never substitute published edition defaults for missing org readings. Do not clamp or hide over-limit values.
2. Record permissions affecting measurement. The [Salesforce Limits reference](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-limits.html) requires View Setup and Configuration for the resource and Manage Users for the storage entries; it also notes a possible five-minute reporting lag. Missing storage entries therefore do not mean unlimited storage or zero usage. Prefer administrator-supplied readings to granting broad rights merely for inspection.
3. Capture relevant custom object/field, permission-set, and license allowances where exposed, distinguishing feature availability from free capacity. Existing API-capable user/license availability is evidence for S05; do not infer a spare paid integration seat. Note Files allowances only as future Phase 1 constraints.
4. Record aggregate existing consumption and, where safely available, project-attributable totals. Keep unrelated records and identifying storage-owner breakdowns out of reports. Unattributable existing use stays unattributed rather than being assigned to this project.
5. Set a documented finite inspection request/page budget before deeper enumeration, using observed headroom and existing org activity. Estimate later search/sync/read-reconciliation and file workloads separately with stated assumptions and reserved headroom. These are planning estimates, not measured production rates or guaranteed capacity.
6. Recommend compact tracking data and local raw jobs/logs/profile evidence/artifact history. Flag inadequate or unknown headroom for SF-04/OPS-01; do not delete data, buy capacity, or move to another org.

**Acceptance examples:** API maximum/remaining and separate data/file storage have units, timestamps, evidence and status; omitted storage entries become a permission/data gap; a rate-limit response stops further API enumeration and preserves partial findings; estimates account for existing use instead of assuming the full allowance belongs to this project.

**Verification:** check arithmetic and source consistency, allowing documented reporting lag; avoid rapid polling merely to obtain matching numbers. **Configuration impact:** recommendations only; no retention or quota enforcement implementation in SF-00.

### SF-00-S05 — Assess existing authentication and no-new-cost options

**Objective:** give SF-02 an evidence-based authentication decision without provisioning an app or user. **Requirements:** R08/R14/R16; R15 constraint. **Dependencies:** S01; S02 access needs; S04 license/capacity evidence. **Owned output:** `authentication.md`.

**Inputs and evidence:** selected existing connection's non-secret metadata; relevant External Client App/Connected App policy views; effective permissions of an existing authorized user; current Salesforce authorization documentation; Python auth/configuration/credential-store code.

**Tasks**

1. Inventory relevant existing app type, ownership, allowed flows/scopes, consent/preauthorization requirements, callback/origin policy, refresh/session expiry and rotation rules, client-secret requirement, certificate presence/expiry if applicable, IP/session restrictions, and API-capable identity availability. Do not reveal consumer secrets, tokens, private keys, account names, or unrelated apps.
2. Separate the connection usable for inspection from one approved for the worker. A CLI session is not proof its app may be reused by Python. Record the necessary existing-user permissions and any licensing restrictions, without requiring a dedicated user or assuming the current user's broad privileges are the intended permanent design.
3. Compare these options, marking each feasible, blocked, or unknown from org evidence:

   | Candidate option | Evidence/prerequisites to assess; no setup in SF-00 |
   |---|---|
   | Existing authorized session | Suitable for bounded inspection only when target/access are verified; record expiry and app-reuse restrictions. |
   | Authorization-code flow with refresh token, PKCE where applicable | Existing user's consent/app policy, callback, required scopes, refresh policy, secret requirements, and secure initial bootstrap. The current provider implements refresh exchange, not a complete authorization-code bootstrap. |
   | JWT bearer | Existing app support, certificate/preauthorization and identity; Windows key protection/rotation; client implementation gap. |
   | Client credentials | Existing app support and permitted execution user/license, scopes and secret handling; client implementation gap. A paid integration-user seat is not a prerequisite assumption. |

4. Recommend one viable path or a conditional decision with precise blockers and alternatives. Current [Salesforce authorization guidance](https://developer.salesforce.com/docs/platform/api-rest/guide/intro-oauth-and-connected-apps.html) recommends External Client Apps and restricts creation of Connected Apps from Spring '26 while allowing existing Connected Apps to continue. Verify actual org policy; do not require replacing a usable existing app. Use [CLI external-client-app guidance](https://developer.salesforce.com/docs/platform/sfdx-dev/guide/sfdx-dev-auth-eca.html) and [client-credentials guidance](https://help.salesforce.com/s/articleView?id=sf.remoteaccess_oauth_client_credentials_flow.htm&language=en_US&type=5) to check option-specific prerequisites at implementation time.
5. Record the native Windows credential-store/execution-account requirement, protected references, expiry/recovery process, and whether the existing provider can honor app policy. In particular, a required client secret or a non-refresh grant needs a downstream client compatibility review. Do not test rotation/revocation or reconfigure the app here. Scheduled unattended authentication remains Phase 2 verification.

**Acceptance examples:** an existing authorized user can be considered without buying a seat; JWT/client credentials are not declared supported merely by changing `auth_flow`; unavailable app-policy visibility produces a specific SF-02 dependency; a valid CLI token does not establish durable worker authentication. Reports contain no credential values.

**Verification:** review the option matrix against actual app/user policy and code, with dated official references. Unverified policy stays unknown. **Configuration impact:** SF-02 owns later app/scopes/permissions/bootstrap choices; SFCLIENT-01 owns any required provider changes.

### SF-00-S06 — Resolve naming risks and propose deployment scope

**Objective:** produce a concrete preservation-first proposal that SF-01/02/04 can implement after their own gates. **Requirements:** R08/R16. **Dependencies:** S02–S05, with unresolved inputs explicitly blocking affected decisions. **Owned output:** `deployment-plan.md`.

**Tasks**

   | Observed case | Proposal |

   | Unrelated/shared/managed member with matching name | Protect it; propose a distinct project name and explicit mapping, or documented use of a supported shared interface. |
   | Visibility or ownership unknown | Hold the affected name and deployment decision pending evidence; no overwrite or assumption of absence. |

3. Produce a logical-to-physical mapping proposal covering every S02 checklist item, candidate versus machine ownership, picklist conversions, and both objects' sync markers. Reference existing mapping schema 1.0; flag incompatible mapping requirements to the owning component rather than revising shared contracts here.
4. Provide an explicit future metadata member allowlist grouped by owner and dependency order: SF-01 schema/identifiers/relationships/defaults; SF-02 minimal permissions and chosen authorization setup; SF-03 only identified UI follow-up; SF-04 retrieval/versioning/capacity follow-up. Separate deployable metadata from manual/nonportable configuration and protected credential material. No wildcards, destructive changes, broad profiles, or unrelated assets. Do not generate a deployable package with unresolved names.
5. Record prerequisites for a later deployment: fresh identity/access/capacity checks, confirmed ownership and mappings, preserved baseline of project metadata, any needed backup of affected project data/candidate fields, supported API version, dependency closure, and component-specific authorization. Describe restoration of the prior project metadata and recovery of affected data as downstream requirements; SF-00 does not execute backup/restore or promise automatic rollback.

**Acceptance examples:** a collision on `Job__c` leads to a reviewed alternate mapping, not replacement; a collision only on a field is still tracked; unknown ownership prevents inclusion; every proposed changed member has an owner/reason/baseline and every unrelated dependency is explicitly protected. Phase 1/2 feature implementation is excluded.

**Verification:** trace each proposal back to inventory evidence; check manifest/member scope by document review only. No deployment validation or write smoke tests. **Migration impact:** identified and handed off, never executed here.

Use small synthetic classification cases if useful; do not create live test records or add implementation-mirroring tests. Any future helper must prove bounded targeting and safe output with offline fixtures before live use. **Configuration impact:** none.

## Missing-access and failure handling

Every gap records attempted scope/source, sanitized error category/code, time, affected output/decision, responsible owner, smallest necessary next action, and exact recheck condition. Continue independent local analysis and available read-only inspection; never fill gaps with invented org facts.

| Condition | Required response and handoff |
|---|---|
| Intended org ambiguous among cached connections | Stop remote access; obtain the target binding from the user. Continue local mapping analysis. Do not probe all cached accounts. |
| CLI unavailable on PATH | Check a known installation path or use existing authorized Setup/API access; document tool gap. Do not require a new org or paid tool. |
| Missing/expired/revoked authentication or required new consent/app setup | Preserve sanitized failure evidence; use existing permitted UI evidence if available. Hand access/bootstrap work to SF-02; never request tokens/passwords in chat or self-grant access. |
| Read/Setup/metadata/limits denied | Mark exact missing capability and affected inventory scope. Request narrowly scoped administrator evidence or authorized access through the owning person/component; do not require blanket administrator rights. |
| Object absent from restricted listing / describe fails | Record unknown visibility versus absence; seek authoritative schema evidence before reserving or deploying its name. |
| Quota exhausted / low remaining allowance | Stop or postpone reads within the recorded budget; retain partial inventory and recheck conditions. Do not retry indefinitely, buy capacity, or delete existing records. |
| Network/service failure | Use bounded read retry only if appropriate; record unavailable evidence rather than treating failure as an empty result. |
| No viable no-new-cost authentication route yet established | Document existing-user and supported-flow alternatives with blockers for SF-02. No paid-user or replacement-org requirement is introduced. |
| Ownership, dependencies, or compatibility unresolved | Exclude affected members from a deployable scope; hand questions to SF-01/SF-04 with evidence needed to resolve them. |

## Handoff checklist and completion gate

- [ ] Component ID/status, objective, R08/R14/R16 traceability and R15 constraints are explicit.
- [ ] Intended existing org is bound privately and represented safely; inspector access and future worker/deployer needs are distinct.
- [ ] All relevant objects/fields, both objects' reconciliation fields, candidate ownership, effective permissions, and constraints are inventoried or explicitly blocked.
- [ ] Project-owned, shared, unrelated, managed, and unknown metadata are distinguished with evidence; dependencies and retrieval completeness are recorded.
- [ ] Actual API/data/file allowances have source, units, timestamps, scope and gaps; no edition-default substitution or zero-budget assumption hides a limitation.
- [ ] Authentication matrix documents existing-user options, app restrictions, Windows credential handling, and actual Python-provider compatibility without exposing credentials.
- [ ] Every naming collision has an evidence-backed disposition; proposed mappings and exact deployment members preserve unrelated assets and candidate-owned fields.
- [ ] Changes made are limited to inventory/handoff artifacts; contracts/configuration versions and migration implications are identified without implementing them.
- [ ] Verification distinguishes local/offline/live/admin-reported/native-Windows results; missing access has an owner/action/recheck condition.
- [ ] **SF-01** receives schema inventory, canonical-ID/lookup constraints, field ownership, naming decisions, baseline and migration questions.
- [ ] **SF-02** receives access matrix, app/flow/user feasibility, minimum permission needs, protected configuration requirements and authentication blockers.
- [ ] **SF-04** receives measured allowances, ownership/dependency inventory, portability/retrieval gaps, baseline preservation and capacity recommendations.
- [ ] **SFCLIENT-01 / SYNC-01** receive verified connection requirements and proposed mappings/compatibility gaps; their earlier offline success is not promoted to live verification.
- [ ] **SF-03 and later owners** receive only relevant discovered UI/automation/Files constraints; no additional component stories or implementation are included.

Planning completion means this story document is saved and reviewed. SF-00 implementation completion requires the evidence and handoff above. Neither implies authorization to deploy or completion of the search-to-Salesforce integration gate.
