## Objective and inspected baseline

Provide one compact Salesforce summary per logical run, keyed uniquely by its UUID, and a completion-notification Flow for successful, empty, partial and failed runs. Repeated delivery, reconciliation and same-run resume must preserve one completion entitlement. Keep full C15 records, pipeline logs, source payloads and attempt history local. AUTO-03 delivers summaries; SF-09 owns the remote schema, validation, notification state, recipient access and Flow behavior.

## Input, output and remote schema contract

Input is AUTO-03's validated, terminal `RunSummaryProjection` plus agreed coverage/version additions, derived from committed C15 and `RunCompletionReceipt`. Output is a Salesforce record ID and queryable applied revision/hash, immutable completion key, notification state and receipt. Record delivery acknowledgment is distinct from notification acceptance; neither proves the candidate read an alert. No synchronous calls to localhost, pipeline execution or model inference occur in Salesforce.

Propose **remote mapping 1.1** to reconcile the current 1.0 gaps. Record exact changes and consumer compatibility with AUTO-03/FND-01 before implementation; do not silently reinterpret existing 1.0 fields or hashes. Existing 1.0 payloads must fail preflight for notification activation until compatibility is explicit. C15 stays at 1.0.

Default object: `Run_Summary__c`, label **Run Summary**, private internal/external sharing, no required Job/Company relationship. Empty and failed searches must be representable without a Job record. Use Text(80) `Name` to match the current adapter; `Headline__c` carries the full display text. A different Name type or collision-driven object name requires explicit mapping. Do not overwrite an unrelated object with the same API name.

All numeric counters are nonnegative Number(18,0), with overflow rejected rather than clamped. Times are DateTime in UTC; display in Europe/Berlin. Core terminal fields are required; unknown companion coverage stays null/unavailable. Unknown is never silently converted to a measured zero.

| Proposed fields | Type / meaning / write owner |
|---|---|
| `Run_Id__c` | Required Text(36), unique case-insensitive External ID, normalized lowercase UUID, immutable. AUTO-03 supplies it; SF-09 validates it. Never key by attempt, status, timestamp or hash. |
| `Contract_Schema_Version__c`, `Mapping_Version__c` | Text(16), C15 version and agreed projection mapping version. AUTO-03 supplies; SF-09 checks supported versions. |
| `Start_Time__c`, `End_Time__c`, `Duration_Seconds__c` | Latest C15 start/end and Number(18,3) duration. End must not precede start. Do not invent an actual crash time from recovery time. |
| `Pipeline_Status__c` | Restricted picklist: `success`, `partial`, `failed`; no success default. AUTO-03/RUN-01 authority. |
| `Headline__c`, `Summary_Text__c` | Text(255) and LongTextArea with application bound 2,000 characters. Plain sanitized summary only. |
| `Source_Postings_Count__c` | Source posting observations, not distinct jobs. |
| `Canonical_Jobs_New__c`, `Canonical_Jobs_Updated__c` | New canonical jobs and existing canonical jobs receiving revisions. |
| `Canonical_Jobs_Duplicate__c` | Duplicate posting observations despite its inherited API name. Label it **Duplicate observations**, never “unique duplicate jobs.” |
| `Eligible_Count__c`, `Review_Count__c`, `Rejected_Count__c` | Canonical jobs evaluated with each disposition under RUN-01 semantics; not a sum of raw source counts. Cached/reused assessments are separate companion information. |
| `Sync_Succeeded__c`, `Sync_Failed__c`, `Quarantined_Count__c` | Logical C12 job-sync operations succeeded/failed and quarantined source records respectively. Summary-delivery retries do not increment them. |
| `Sources_Attempted__c`, `Sources_Succeeded__c`, `Sources_Failed__c` | Bounded display lists of safe source keys, at most 1,000 characters each. Preserve incomplete-source meaning; not raw URLs or responses. |
| `Source_Counts__c`, `Stage_Counts__c` | Proposed bounded structured text, at most 2,000 characters each: source key → observed postings; stage key → count, unit, terminal state and known/unknown coverage. AUTO-03 obtains stage data from persisted RUN-01 evidence, not C15 defaults. No per-record events or stage logs. |
| `Coverage_Status__c`, `Projection_Truncated__c` | Proposed restricted `complete`, `partial`, `unavailable` and Checkbox. Coverage refers to configured scopes, not the whole German job market. Missing stage evidence is explicit. Truncation keeps valid structured data, stable ordering and an omitted-entry count; totals remain exact. |
| `Error_Summary__c`, `Pending_Work_Summary__c` | Sanitized plain text bounded to 500 characters each; nullable. AUTO-03 sends explicit null to clear obsolete latest-result text. No raw `ClassifiedError`/pending-work list serialization. |
| `Revision__c`, `Payload_Hash__c` | Positive monotonic revision and Text(64) canonical SHA-256 over all delivery-owned projection fields under a documented hash version. Same revision with different content is a conflict. Server-owned notification changes are excluded. |
| `First_Completion_Key__c`, `First_Payload_Hash__c` | Required immutable Text(80) unique key and Text(64) first-result hash. Key is canonical verified org ID + `:` + run UUID; validate org against the receiving org, normalize 15/18-character ID representation consistently. Not a new key on resume. |
| `First_Completed_At__c`, `First_Status__c`, `First_Headline__c`, `First_Summary_Text__c` | Immutable first terminal end time, status and bounded safe display snapshot. SF-09 freezes these at first accepted completion. Initial delivery must carry the first snapshot if its latest revision is already newer; never reconstruct it from the latest result. |
| `Completion_Recorded_At__c` | Salesforce-owned DateTime of first accepted terminal receipt; distinct from actual run end. Written once. Its transition from blank to populated admits one entitlement. |
| `Notification_Recipient__c` | Proposed Lookup(User), Salesforce-owned resolved/snapshotted recipient, configured by an authorized operator. Do not accept arbitrary email/group strings from a summary. |
| `Notification_Status__c` | Salesforce-owned restricted states `none`, `pending`, `dispatching`, `confirmed`, `failed`, `unknown`, `suppressed`. No `updated` status. Separate from pipeline outcome. |
| `Notification_Claim_Id__c`, `Notification_Attempt_Count__c`, `Notification_Last_Attempt_At__c`, `Notification_Next_Attempt_At__c` | Server-owned durable dispatch ownership and bounded retry markers. One active claim per completion key; identity survives restart/redeployment. |
| `Notification_Receipt_Id__c`, `Notification_Accepted_At__c`, `Notification_Error_Code__c` | Server-owned Text(80) receipt, DateTime and bounded allowlisted code. Receipt is immutable once confirmed. It attests to recorded platform acceptance, not human delivery/read; do not fabricate a platform notification ID. |

LongTextArea storage may require a larger metadata length than these application bounds. Enforce the smaller limits in the agreed projection validator and server guard; do not depend on field capacity alone. Retain a bounded remote record, not serialized full C15/errors/history. Detailed source/stage dictionaries and omitted diagnostics remain locally inspectable by `run_id`.

`Is_First_Completion__c` from the AUTO-03 handoff is not authoritative. Omit it from the chosen schema or retain only as a compatibility hint after agreement; a client Boolean can never grant/regrant entitlement. Server timestamps, receipt and claim are not writable by the summary worker. A client cannot reset them by PATCH, null clearing or setting status back to pending.

**Revision rules:** allow identical same-revision replays as successful no-ops, preserving notification markers; reject lower revisions and same-revision/different-payload conflicts with safe errors. Accept higher revisions only with unchanged run/completion identity and first snapshot, updating latest-result fields silently. Enforce comparison and update in one serialized server operation, including concurrent inserts/updates. Unique External ID handles identity, but does not alone enforce ordering. Validate supplied hashes against the agreed canonical content or compare all relevant fields server-side; an unchanged client hash cannot conceal modified content.

**Acknowledgment rules:** AUTO-03 reads `Id`, run ID, revision, payload hash, completion key and notification fields from the record. Missing record is distinct from unauthorized/malformed/unsupported access. Upsert success alone leaves notification pending/unknown until server evidence is read. Map `dispatching` to local pending, `confirmed` to confirmed, `failed` to failed and `unknown` to unknown; add an explicit suppressed mapping to the companion contract or documented non-success disposition. Never report suppressed/unknown as confirmed. Keep original pipeline status and process exit code unchanged by notification failure.

## Completion and notification behavior

| Run case | Required result and alert |
|---|---|
| Successful nonempty | `success`; display measured observations, new/updated jobs, duplicate observations and dispositions. Admit one alert, linking to the summary. |
| Empty successful | `success`; “No postings found” only with authoritative complete configured-source coverage and zero observations. Observed duplicates/updates with zero new jobs mean “No new jobs.” Zero eligible jobs is not an empty search. |
| Partial | `partial`; clearly identify incomplete sources/stages, known counts, safe error digest and pending work. Zero useful output does not make it successful/empty. |
| Failed | `failed`; link to the standalone summary with bounded actionable diagnostics and known progress. Missing counts/coverage are labeled unavailable; a Job record is not required. |
| Same-run resume | Keep UUID/key and first snapshot; apply a higher latest-result revision silently, even for failed → success. If the first alert is delayed, identify its first-result time/status and show that newer results are available on the record. |
| New deliberate run | New UUID and new entitlement, even when every input/count equals an earlier run. |
| Running or unadmitted invocation | No completion marker/alert. An interrupted admitted run becomes eligible only after RUN-01 has durably finalized/reconstructed a trustworthy terminal receipt. |

Propose `JA_Run_Completed` CustomNotificationType and `JA_Run_Summary_Completion` after-save Flow, plus an SF-09-owned guarded dispatch subflow/helper where needed. Use a fixed title selected by first status and a bounded body containing safe counts, first completion time and a link to `Run_Summary__c.Id`. Show latest and first result separately on the record. Do not put free-form errors, raw source text or candidate data on the notification surface. Navigation opens an authenticated summary; it does not rerun work or trigger generation.

Salesforce's custom notification action accepts recipient IDs and a record target, with title/body bounds of 250/750 characters. Use tighter templates; the stored 255-character headline is not copied blindly into a notification. A custom notification type must exist before sending. See [Salesforce Custom Notification Actions](https://developer.salesforce.com/docs/platform/api-action/guide/actions-obj-custom-notification.html) and [Flow notification example](https://help.salesforce.com/s/articleView?id=platform.automate_flow_build_example_send_custom_notification.htm&language=en_US&type=5). Recheck capabilities against API 60.0 and the actual org at implementation time. These references do not establish atomic send/receipt semantics.

The following is the required dispatch protocol; the platform transaction proof is an implementation gate:

1. Validate and serialize summary admission. On the first trustworthy terminal result, freeze completion identity/content, record `Completion_Recorded_At__c`, and establish one pending entitlement. Duplicate upserts never create a new entitlement. Completion time/status changes and `ISCHANGED(Pipeline_Status__c)` are not notification gates.
2. Commit summary admission before notification side effects. A separate dispatch execution re-reads the record and verifies enabled configuration, activation epoch, a single configured active recipient, record access, immutable key and no accepted/uncertain claim. Missing recipient/access/type/configuration holds unsent work visibly; there is no owner/admin/group fallback.
3. Acquire a serialized claim and persist attempt identity before possible send. An asynchronous Flow path alone is not proof of mutual exclusion. Implement a small bulk-safe SF-09 Apex invocable/dispatcher if needed for row locking, unique claim and transaction boundaries. Keep notification selection/content/fault routing in the Flow. Do not broaden AUTO-03 into a remote sender.
4. Prove either atomic send-plus-receipt behavior, or a committed pre-send fence with exclusive, non-replayed attempt ownership. Concurrent upserts/Flow interviews must not both invoke the action. The receipt is recorded only after confirmed acceptance. Marker updates must not recursively wake another send.
5. A timeout, crash, rollback after possible send, or abandoned dispatch claim becomes `unknown`. Preserve the fence and hold it; neither lease expiry, summary replay, Flow redeployment nor an operator's generic retry can automatically resend. Resolve only from evidence of acceptance or proven non-send. If that evidence is unavailable, leave the possible missed alert visible rather than claiming exactly-once delivery. If the fence cannot be demonstrated, keep notification activation blocked.
6. Retry only proven pre-send failures under the same completion key. Proposed bound: three retries after the initial attempt, at 1, 5 and 30 minutes, subject to platform limits. Permission/configuration failures wait for repair; exhaustion stays inspectable as `failed`. A scoped admin preview/retry operation is sufficient initially; any remote timed recovery must be explicitly packaged and tested. Summary upserts are not the retry scheduler.
7. Confirmed receipts and first identity are permanent through newer revisions, status re-entry, restoration and reactivation. Disabling notifications stops dispatch, including queued work that has not sent. Re-enabling requires a bounded backlog decision; never mass-reset markers. Old/historical imports are suppressed by default with an explicit reason; they cannot pretend to have an acceptance receipt.

This guarantees one entitlement and prevents duplicate alerts from repeated summary upserts. It does not promise exactly-once network delivery or immediate notification during outages. Summary delivery, notification acceptance and candidate reading remain separate observations.
