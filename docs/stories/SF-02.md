# SF-02 — Integration authorization for the native Windows worker

Status: **PLANNED — live capability and dependency verification pending** · Planning date: **1 November 2026** · Phase 0 · Scope: **SF-02 only**

Baseline: [IMPLEMENTATION_BLUEPRINT.md](../../IMPLEMENTATION_BLUEPRINT.md), especially §§1–2, 5–10. Direct requirements: **R08** (tracking without overwriting candidate decisions) and **R15** (credential and data protection). R14 and R16 constrain Windows operation, cost, recovery and audit evidence.

**Selected design:** a dedicated, local External Client App (ECA), OAuth authorization code/web server flow with **PKCE S256**, followed by refresh-token renewal. Use a restricted Salesforce user covered by an **existing, verified no-additional-cost entitlement**. Do not require purchase of a Salesforce Integration license. Store the refresh token with current-user Windows DPAPI; do not distribute a client secret or generate a signing key for this flow.

This is a selection for implementation, **not a claim that the org supports the required configuration today**. SF-00 contains no live inventory. SF-01 metadata, supporting documents and its implementation handoff appeared during this task and were read before completion; that handoff reports local implementation with live deployment/verification pending. Available access did not permit authenticated org inspection during this task. The stories below make the remaining capability, licensing and permission checks release gates. This task changed no org access, credentials, records, metadata or runtime configuration; its only authored file is this story document. Concurrent SF-01 workspace additions were read, not modified.

### No-additional-cost identity decision

Inspect Company Information license totals/used counts, eligible license features, and the proposed user's effective permissions. Prefer an existing restricted account, or a dedicated worker account using a demonstrably available included license. Record license type, entitlement evidence and incremental cost **zero**; do not infer spare capacity from Developer Edition defaults or assume all full-user licenses imply an Admin profile.

The candidate keeps a separate identity with candidate-field edit rights. The worker must not inherit these rights from a shared profile, permission set/group, role, sharing rule or elevated system permission. Permission sets add to profile access; they do not subtract an administrator's access. [Salesforce permission and field-security guidance](https://trailhead.salesforce.com/content/learn/projects/keep-data-secure-in-a-recruiting-app/fls-perm-sets-sharing).

If no suitable existing/included entitlement is available, leave **live authorization blocked** and retain offline execution. Do not purchase a seat, deactivate another user, downgrade the candidate/admin, or substitute an administrator token. An administrator-only demonstration would be explicitly nonconforming for negative access acceptance. This plan does not claim a fully verified zero-cost restricted identity is currently available.

## Windows credentials and token lifecycle

Use one explicit non-admin Windows execution account for enrollment and worker execution. Default private data root: `%LOCALAPPDATA%\JobAutomation`; credential directory: `data_root/credentials`, outside the repository. In PowerShell construct it with `Join-Path $env:LOCALAPPDATA 'JobAutomation'`. Resolve runtime paths through AppConfig, independently of the current directory; use `pathlib.Path` in Python. Test spaces and non-ASCII path segments.

Current-user DPAPI binds encryption to the Windows user's logon credentials and usually the machine. Do not use `CRYPTPROTECT_LOCAL_MACHINE`. Apply/verify NTFS protection on the credential directory, ciphertext, temporary files and exchange markers; allow the worker identity and necessary OS administration only, with no broad Users/Everyone access. DPAPI does not protect against malicious code running as that same identity or an administrator. [Microsoft DPAPI reference](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

| Material / event | Required behavior |
|---|---|
| Client ID | Public identifier, but provision through `client_id_ref` to fit the existing interface. Namespace references by org/user/app installation, not one ambiguous global token slot. |
| Refresh token | Persist only DPAPI ciphertext under `credential_ref`; never in JSON, SQLite, environment variables, process arguments, shell history, chat, clipboard instructions, logs or ordinary backups. |
| Access token | Memory only; minimize lifetime and avoid object repr/exception dumps. Cache until expiry (with existing skew) or explicit invalid-session response; do not invent a lifetime when `expires_in` is absent. Python strings cannot promise guaranteed zeroization. |
| PKCE verifier/state/code | Fresh high-entropy values, memory only, one enrollment attempt, short timeout. Verify state and exact callback before code exchange; reject replay, missing state or mismatched verifier. Disable callback request logging and remote resources; close listener after success/failure. |
| Client secret / signing key | **Not required or stored for the selected flow.** No PEM/PFX generation or secret-viewing grant. If JWT is later selected, separately specify non-exportable Windows CNG/certificate-store signing or DPAPI-encrypted key material, public-cert upload, thumbprint, expiry/overlap rotation and signer compatibility. Current client does not support this. |
| Initial enrollment | User authenticates/MFA in the system browser as the restricted Salesforce user. Helper never collects the Salesforce password/security token. Exchange code via HTTPS POST with PKCE and exact redirect URI; verify returned origin and live org/user IDs before activating protected credentials. Wrong identity must not overwrite the previous working store. |
| Refresh | Serialize across every process/helper using the credential, including smoke checks. Persist the exchange marker before sending; atomically replace the rotated refresh token before exposing the new session or clearing the marker. Keep bounded sends; no blind replay after uncertain transmission. |
| Expiry / rejection | One bounded renewal on invalid session. `invalid_grant`, revocation, disabled user/app, missing scope or persistent authentication failure becomes actionable reauthorization-required; no password fallback or retry storm. Distinguish 403 permission denial from quota exhaustion. |
| Crash / ambiguous exchange | Preserve pending marker and stop. Reauthorize to obtain a new grant; do not clear the marker and retry the old token simply because a process restarted. A stale credential backup can trigger rotation reuse detection. |
| Rotation policy | Enable only once single-writer locking and crash-safe persistence are verified. Refresh-token replacement alone is not proof of concurrent safety. Document observed effective expiry under rotation and any idle TTL. |
| Disconnect / compromise | Stop all worker entry points; revoke the refresh token through the verified HTTPS revocation endpoint, or revoke the specific app/user grant in Setup when local tokens are unavailable. Then clear in-memory sessions and remove local credentials/markers. Verify deletion results; current store suppresses some unlink failures. Local deletion alone does not revoke server access. |
| Offline revocation | Mark revocation pending and keep worker disabled; do not report success because local files disappeared. Use administrator revocation on the next available trusted connection. Do not delete the sole revocation material prematurely. |
| Recovery / machine change | Reauthorize under the intended Windows identity; ordinary app backups exclude credentials. Do not restore an old rotating token or promise DPAPI ciphertext is portable. No automatic logged-out/reboot claim: AUTO-01 must later verify the same identity/profile and task logon mode. |

Salesforce's revoke endpoint accepts a token in a form-encoded POST body; revoking a refresh token also revokes associated access tokens. Assignment removal or disabling a grant type is not a substitute for explicit session revocation. [Revocation reference](https://developer.salesforce.com/docs/platform/mobile-sdk/guide/oauth-revoking-tokens.html).

## Deployment, rollback and handoff gates

Salesforce ECA configuration spans multiple metadata types. Its header is `ExternalClientApplication`; OAuth settings and generated subscriber policies are separate. Global OAuth settings can contain sensitive consumer information and must not be committed. [Salesforce metadata relationships](https://developer.salesforce.com/docs/platform/pkg2-dev/guide/packaging-packageable-components.html), [ECA policy lifecycle](https://developer.salesforce.com/blogs/2025/01/secure-your-org-with-external-client-apps).

Use exact, inspected members under `externalClientApps/`, `extlClntAppOauthSettings/`, applicable OAuth policy directories and `permissionsets/`; confirm path/type support with the selected Metadata API. Keep sensitive global OAuth files and generated credentials outside tracked source. A sanitized template/checklist may describe their settings. No broad Profile retrieval/deployment, wildcard manifest, destructive package, unrelated sharing rules, consumer-key rotation or automatic user assignment.

Future authorized implementation sequence:
