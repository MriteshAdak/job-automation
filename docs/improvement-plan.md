# Project Improvement Plan

Assessment date: 3 November 2026. This plan describes proposed work based on the current checkout; the runtime and framework changes below have not been implemented. Historical verification reports are evidence to revisit, not results reproduced during this review.

Prioritize a reproducible installation and a complete generation workflow. Then evaluate Hugging Face Transformers as an optional local model backend. Introduce LangChain or LangGraph only where a specific integration or workflow requirement justifies their additional dependencies. The existing component boundaries support this approach.

The component assessment below distinguishes concrete gaps from conditional improvements. P0 enables reliable execution, P1 establishes end-to-end evidence, and P2 covers changes whose value must first be demonstrated.

Hugging Face Transformers fits behind the existing model interface. The proposed benefit is direct control over model revisions, tokenizers, chat formatting, and decoding. It does not establish better relevance, factuality, speed, or memory use by itself. The archived hardware report describes a 4 GB GTX 1650 and 16 GB system RAM; measure the actual deployment machine before selecting a Transformers/PyTorch configuration.

The migration should proceed as follows:

1. Add a provider factory used by assessment, context indexing, generation, and evaluation. Keep `ModelCall`, `ModelResult`, embedding responses, audit records, and classified errors as the application boundary. Extract shared validation and retry behavior from the Ollama-specific harnesses.
2. Implement an optional local Transformers provider with pinned model and tokenizer revisions, recorded precision/quantization settings, and model-specific prompt formatting. Use exact tokenizer counts for the complete formatted prompt and completion reserve. Transformers provides model-specific [chat templates](https://huggingface.co/docs/transformers/en/chat_templating).
3. Predownload model artifacts and configure offline inference. Preserve local execution through a supervised worker process with bounded concurrency, health checks, and enforceable deadlines. Transformers supports [offline loading](https://huggingface.co/docs/transformers/en/installation); its `max_time` may finish the current pass, so it does not provide a hard process deadline. See the [generation API](https://huggingface.co/docs/transformers/en/main_classes/text_generation).
4. Preserve strict JSON parsing, schema validation, evidence checks, and bounded retries. Explicitly map supported generation settings and reject unsupported ones. Treat structured-output behavior as a capability to implement and test; model loading alone does not replace the existing Ollama schema-request behavior.
5. Implement embeddings with the selected model's required pooling, normalization, ordering, and provenance. The current MiniLM family documents attention-mask-aware mean pooling and normalization for direct Transformers use in its [model card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2). Rebuild indexes when model revision or preprocessing changes; equal vector dimensions do not establish compatibility. Preserve the existing [embedding-space fingerprint](../src/job_automation/context/index_identity.py).
6. Generalize benchmark and supervisor code that currently calls Ollama endpoints. Compare backends on fixed evidence and tasks, recording model revisions, quantization, prompts, settings, cold/warm latency, peak RAM/VRAM, schema success, evidence fidelity, and retrieval quality. Include full CVs and cover letters, CPU fallback, and timeout recovery.

Change the default backend only after the candidate meets correctness and resource requirements and demonstrates a useful improvement or required capability. Set evaluation thresholds before running the comparison. Keep Ollama selectable during rollout, retain its compatible indexes, and pin a backend/model to each in-flight request so a rollback cannot silently change frozen inputs.

LangChain is an optional integration layer. Its [Hugging Face pipeline integration](https://docs.langchain.com/oss/python/integrations/llms/huggingface_pipelines) can wrap a local Transformers pipeline, but the project can also call Transformers directly. Use a thin adapter behind `ModelProvider` or the retrieval interfaces only when a named integration removes enough maintained code to justify the dependency. Preserve evidence IDs, purpose restrictions, prompt budgets, validation, and audit records. The acceptance criterion is a demonstrated integration benefit with unchanged contract behavior; a second abstraction around an already working call is insufficient justification.

LangGraph is a conditional workflow option. It supports stateful orchestration and can be used independently of LangChain, as described in its [overview](https://docs.langchain.com/oss/python/langgraph/overview). The current runner already provides stage checkpoints, recovery, locks, and delivery reconciliation. First connect and verify those services. A graph pilot becomes useful if an actual requirement introduces branching, bounded draft revisions, or resumable user interactions that are cumbersome in the current coordinator.

For that pilot, wrap existing generation service calls and store stable request IDs and receipt references in graph state. Define one owner for execution checkpoints, while keeping business records, delivery intents, and outboxes authoritative in the application database. Use persistent checkpoints for restart recovery; [in-memory checkpoints disappear on restart](https://docs.langchain.com/oss/python/langgraph/persistence). Keep worker locking and remote reconciliation: resuming an [interrupt restarts its node](https://docs.langchain.com/oss/python/langgraph/interrupts), so uploads and notifications must remain idempotent. Graph execution must preserve explicit human approval.

Adopt the graph pilot only if it simplifies a concrete new branch and passes the existing crash/retry cases without duplicate uploads, notifications, or approval changes. Measure its runtime overhead and retain a selectable existing coordinator until restart and rollback behavior are demonstrated. LangChain and LangGraph are separate adoption decisions.

Delivery should follow this order:

| Stage | Deliverable | Completion evidence |
| --- | --- | --- |
| 1. Reproducible baseline | Packaging, optional dependency groups, repository cleanup plan, and Windows CI. | A clean checkout installs and runs CLI diagnostics and offline tests without the committed virtual environment. Record platform-specific skips. |
| 2. Connected workflow | Generation service assembly, configuration preflight, and a CLI-driven integration scenario. | A request passes through freeze, context, draft, validation, rendering, and delivery using real application services with controlled external transports. Missing dependencies fail clearly before work is admitted. |
| 3. Live acceptance and quality baseline | Controlled source/Salesforce/model/LibreOffice checks, expanded evaluation corpus, restore and startup drills, and a current status index. | Record commit, configuration, platform, model revisions, outcomes, and skipped checks. Demonstrate recovery without duplicate remote effects and drafts remaining subject to human approval. |
| 4. Transformers experiment | Optional provider, backend-aware supervision and benchmarks, and an explicit adoption decision. | Compare against Ollama under preset correctness, quality, memory, and latency criteria. Exercise rollback and embedding-index compatibility. |
| 5. Framework experiments, if justified | A narrowly scoped LangChain adapter or LangGraph branch pilot. | Identify the concrete requirement, show reduced implementation burden, and pass contract, recovery, and performance checks before adoption. |

Use the existing manual smoke scripts and evaluation isolation for these checks. Keep source expansion conditional on measured coverage, and keep SQLite, deterministic eligibility, evidence validation, and human review as the foundation unless new measurements reveal a specific limitation.
